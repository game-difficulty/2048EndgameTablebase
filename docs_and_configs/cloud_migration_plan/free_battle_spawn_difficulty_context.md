## 1. 任务目标

自由吻合度对战允许各玩家从相同初始盘面和随机种子出发，按照自己的方向选择发展独立棋盘。服务器查询当前局面的定式成功率、判断玩家走法是否需要纠正，并为移动后的棋盘选择一个出数。

本模块接下来要解决的问题是：

1. 不再只限制出数“不能太坏”，还要避免某些玩家长期获得过于简单的出数。
2. 不同玩家虽然走入不同路线，仍应承受大致相当的外生出数难度。
3. 不把成功率的大幅下降或回升直接误判为玩家决策难度。
4. 保留自然的出 2 / 出 4 概率、确定性、公平性、预取能力和可接受的单步延迟。
5. 玩家自己选择次优方向造成的风险不能由系统通过后续简单出数过度补偿。

本任务不是简单地把 `1.15 / 1.20` 改成另一组常数。需要先建立可解释、可比较的难度指标，再设计候选选择算法。

## 2. 项目与模式背景

### 2.1 相关架构

- 前端：Vue 3，Battle 页面通过 WebSocket 发送方向和接收结算结果。
- 后端：FastAPI/WebSocket；自由对战由服务器负责移动判定、查表、纠正、出数和权威状态持久化。
- 定式查询：本机云表或远程 tablebase worker，统一经过 `backend/tablebase_query_service.py`。
- 查询调度器具备前台/预取队列、去重和服务器内存缓存。
- 当前服务器结果缓存上限和 TTL：由 `backend/tablebase_query_service.py` 配置，现实现为 5 分钟缓存。
- 模式 key：`free_goodness`；当前模式版本为 2。

### 2.2 自由对战核心规则

- 各玩家独立发展棋盘，不共享固定路线。
- 当前棋盘查表后会得到四个方向的成功率；最优方向同分顺序固定为：`left > right > down > up`。
- 非法方向不推进。
- 合法方向可能被纠正为最优方向：
  - 玩家方向成功率为 0 时必定纠正；
  - 或死亡率相对增幅超过 15%，且死亡率绝对增幅至少为 0.002（0.2 个百分点）时纠正。
- 单步吻合度沿用 Tester 语义：`selected_success / best_success`。
- 累计吻合度是所有计分步骤单步吻合度的乘积，不是算术平均。
- 查询和网络解析期间，服务器将玩家状态设为 `resolving` 并暂停单步倒计时。
- 普通未纠正移动完成后无需第二次 ACK；纠正浮层仍保留继续确认流程。
- 房主承担自由对战查表预算；不要在本模块中改变计费语义。

## 3. 当前出数算法

### 3.1 每局种子

每局创建时使用 `secrets.token_hex(32)` 生成 256 位 `route_seed`。同一局所有玩家共享该种子，新一局生成新种子。

### 3.2 确定性候选

玩家方向执行后，服务器得到尚未出数的 `moved_board`。候选由下式确定：

```text
ticket = HMAC-SHA256(route_seed, moved_board || attempt_index)
```

- ticket 前 8 字节决定空格位置。
- ticket 接下来的 8 字节按 tablebase catalog 的 `spawn_rate` 决定 2/4。
- 当前所有已上线 catalog 表的 `spawn_rate` 通常为 0.1，即初次抽取为 90% 出 2、10% 出 4。
- `(位置, 数值)` 候选不重复；发生重复抽取时，从尚未尝试的组合中确定性选一个。
- 候选最多遍历 `空格数 × 可生成数值数`。

当前 ticket 不包含玩家、步数或方向，只包含本局种子、移动后棋盘和候选序号。因此同一局中相同 `moved_board` 会产生相同候选顺序。

注意：最终接受哪个候选还依赖 `executed_success` 和该玩家累计 `SpawnRiskState`。相同棋盘但风险历史不同，最终出数仍可能不同。

### 3.3 当前风险筛选

设：

```text
Q_exec = 已执行方向在出数前的成功率
V_next = 候选出数后棋盘的最优方向成功率
death(p) = 1 - p
spawn_multiplier = death(V_next) / death(Q_exec)
```

特殊情况下按现有 `risk_multiplier()` 规则处理成功率 1、0 和无穷值。

候选必须同时满足：

```text
spawn_multiplier <= 1.15
累计死亡率最大回撤 <= 1.20
```

累计回撤由 `SpawnRiskState` 在 log 空间维护。候选查表未命中也会被跳过。

如果玩家方向找不到可接受出数，而该方向不是最优方向，服务器会改用最优方向重新寻找。如果最优方向仍没有候选，则不生成棋块，并以 `risk_boundary` 结束该玩家对局。

### 3.4 当前预取

- 当前局面确定后，服务器预取最优方向，以及不会触发移动纠正的其他合法方向。
- 不值得执行、必然会被纠正的方向不预取。
- 各方向并行处理；每个方向从候选序列开始查找，找到第一个满足当前风险上限的候选便停止。
- 预取按 `round_id + actor_key + sequence + board + catalog_version` 缓存在内存中，上限 2048 个状态。
- 玩家输入命中预取时直接使用；未命中则进入 foreground 查询。
- 本步完成后异步调度下一状态的预取。

## 4. 已确认的设计问题

### 4.1 当前只有上限，没有难度下限

`1.15 / 1.20` 只防止路线突然恶化。算法接受“第一个不过分坏的候选”，因此一个玩家可能长期得到非常有利的出生位置，而另一个玩家只得到刚好不超过上限的结果。

### 4.2 当前指标不是决策难度

成功率或死亡率的变化主要描述局面风险，不直接描述人类是否难以选择方向。

典型反例：一个差出数（经常是 4）可能令成功率从正常水平跌到约 10%，表示后面必须赌一次 4；如果下一步真的出了 4，成功率又会回升。两步成功率变化都很大，但如果过程中只有唯一合理走法，玩家实际上没有选择难度。

### 4.3 原始成功率不能跨 layer 直接比较

同一个成功率在不同定式、不同 layer 的意义不同。应比较“当前局面相对于该定式同 layer 主流路线的位置”，不能只比较 80%、50% 等绝对值。

### 4.4 重抽会改变实际概率分布

第一个候选遵循 `spawn_rate`，但危险候选会被拒绝；重复候选的 fallback 又从剩余 `(位置, 数值)` 组合中选择。最终实际出 2/4 和位置分布是经过风险条件筛选后的分布，不再严格等于原始自然分布。

### 4.5 不应奖励玩家自己的失误

玩家走入较差路线后，其绝对成功率更低是玩家行为的结果。出数控制只能平衡“给定移动后棋盘上的外生出数难度”，不应为了拉齐双方绝对成功率而给落后玩家明显更好的出数。

## 5. 推荐的难度指标体系

不要立即压缩成单一分数。至少保留以下四个维度，先观察分布，再决定组合方式。

### 5.1 局部出数逆风度 `spawn_adversity`

这是建议作为出数公平控制的主指标。

对于同一个 `moved_board`，枚举或确定性采样可能的出生结果，查询每个候选的 `V_next`。按真实概率加权：

```text
每个空位等概率
数值按 spawn_rate 加权（通常 2 为 0.9、4 为 0.1）
```

令当前候选的成功率处于该局部候选分布的加权百分位 `F_local(V_next)`：

```text
spawn_adversity = 1 - F_local(V_next)
```

- 接近 0：相对当前移动后棋盘很有利。
- 接近 1：相对当前移动后棋盘很不利。

该指标不要求不同路线具有相同绝对成功率，只比较各玩家“本来可能得到的出生结果”，适合控制难度上下限。

### 5.2 同 layer 局面质量 `layer_quality`

为每个 `full_pattern + layer` 离线建立最优路线或主流路线成功率分布：

```text
layer_quality = 当前最优成功率在同表同 layer 基线中的百分位
```

它用于判断局面是否比主流路线略差、明显偏差或异常好。profile 必须按完整定式区分，不能把 L3、free10、variant 等混为一组。

需要先确认各类 BookReader/native reader 能否稳定返回实际 layer；若不能，应新增统一的只读 layer helper。不要擅自用游戏分数替代 layer。

### 5.3 决策结构

将合法方向成功率排序为 `p1 >= p2 >= p3 >= p4`，对每个候选方向定义：

```text
log_regret_i = -ln(p_i / p1)
tester_loss_i = 1 - p_i / p1
```

至少分别记录：

- `choice_ambiguity`：多个方向是否足够接近，以至于难以辨认。
- `mistake_consequence`：误选一个看似合理方向会造成多少吻合度损失。
- `positive_choice_count`：成功率大于零且不是明显自杀的方向数。
- `forced`：只有一个合法/有效方向时为真，此时决策难度应视为低，即使成功率剧烈变化。

不要只使用 `p1-p2`。较差局面中 `50% vs 35%` 仍可能难判断；较好局面中 `76% vs 70%` 可能已经代表较明确的短期错误；`76% vs 75.3% vs 75%` 则有很高选择歧义但较低单步惩罚。

在没有人类走法数据前，不应宣称某个固定公式已经代表“人类难度”。可先保留 ambiguity 和 consequence 两轴；以后使用 Tester/对战匿名聚合数据校准。

### 5.4 路线罕见度 `state_rarity`

定式查询本身不提供可靠访问频率。建议离线执行大量“自然出数 + 最优走法”模拟，按 `full_pattern + layer` 统计 canonical board 或结构特征的访问频率：

```text
state_rarity = -log(visit_probability)
```

精确棋盘未命中时可退化到结构分桶，例如空格数、大块位置、单调性、合法方向数、四方向成功率向量等。罕见度是辅助指标，不应单独决定出数。

### 5.5 出数波动性

记录当前 `moved_board` 所有候选出数的 `V_next` 分布范围、IQR 或百分位跨度。它表示该局面有多依赖出数运气，与玩家决策难度分开。

## 6. 推荐的新候选选择模型

### 6.1 共享“难度脚本”，而非共享路线

每个步数由本局共享种子生成：

```text
spawn_value       本步生成 2 或 4
target_adversity  本步目标局部逆风百分位
target_choice     希望进入的决策难度区间
```

不同玩家在相同步数使用相同目标，但基于自己的 `moved_board` 选择具体位置。这样保持独立路线，同时使玩家面对的相对外生难度接近。

建议优先固定 `spawn_value`，再比较位置。这样能严格保持共享步骤上的 90%/10% 数值序列，也能把候选查询量大致减半。

### 6.2 上下限和软目标

不要使用“找到第一个小于上限的候选”。应在有限候选中计算指标，然后：

1. 排除真正不可接受的安全边界候选。
2. 对过难和过易都设置软惩罚。
3. 选择最接近本步共享目标的候选。
4. 没有候选落在理想区间时，选择距离最近者，而不是无限重抽。

初步可研究局部逆风百分位 20%–80% 之类的区间，但这些数值不能直接上线，必须根据离线 profile 校准。

### 6.3 滑动窗口难度债务

逐步完全一致不现实，也会导致候选选择僵硬。建议按 8–16 个计分步骤维护外生难度债务：

```text
difficulty_debt = decay * previous_debt + target_difficulty - actual_difficulty
```

后续选择略微修正累计偏差。债务只包含系统出数难度，不包含玩家方向造成的吻合度损失，不应形成动态追赶补偿。

### 6.4 “赌 4”强制段的处理

- 成功率急跌：可以记录为高 `spawn_adversity` 或高运气波动。
- 下一状态只有唯一有效方向：`forced=true`，决策难度低。
- 后续因幸运 4 回升：属于有利出数，不应作为一次困难决策。
- 可将连续 forced 状态视为一个风险 excursion，仅记录该段最大外生回撤，避免把跌落和恢复重复计作两次难度。

## 7. 性能与查询预算

完整枚举最多需要 `空格数 × 2` 次查表；再乘多个合法方向会放大预取压力。建议：

1. 先固定本步 2/4，只评估出生位置。
2. 空格不超过 4 时枚举全部位置。
3. 空格较多时按共享种子确定性采样最多 4 个位置。
4. 先预取最优方向和最可能被执行的方向，再处理其他允许方向。
5. 继续复用 `tablebase_query_scheduler` 的请求去重、前台优先级和 5 分钟结果缓存。
6. 玩家输入命中预取时不得增加第二次 RTT 或额外 ACK。
7. 预取失败必须允许 foreground 补查；队列过载时保持赞助者优先级策略。

候选样本数、方向数和 profile 精度之间需要用真实服务器时延与 worker 吞吐量评估，不能只追求理论上完整枚举。

## 8. 建议实施顺序

### 阶段 A：离线画像和固定夹具

- 为每类定式确定统一 layer 获取方式。
- 使用本地定式运行大量自然出数、最优走法模拟。
- 按 `full_pattern + layer` 输出紧凑 profile：成功率分位、方向 gap 分布、访问频率和候选出数波动。
- 建立典型夹具：主流路线、坏出数路线、强制赌 4、低成功率自然死亡、variant 棋盘。

### 阶段 B：影子计算

- 保持线上选择结果不变，只在测试或离线 replay 上计算新指标。
- 对比当前接受候选与新算法候选，不写大量生产日志。
- 输出聚合分布，确认指标确实将 forced 赌 4 与困难决策区分开。

### 阶段 C：候选选择器 v2

- 新增独立 difficulty profile/selector 模块，不把复杂公式继续堆入 `runtime.py`。
- `rules.py` 只保存纯函数和不可变数据结构。
- `runtime.py` 负责查询、预取、状态事务和调用 selector。
- 通过 mode version 或服务端 feature flag 灰度，旧进行中回合继续使用旧规则。

### 阶段 D：模拟与上线

- 使用相同初始盘面和共享种子模拟两条不同玩家路线。
- 比较双方局部逆风度、决策难度和滑动窗口难度差。
- 验证 2/4 分布、自然死亡率、平均查询数、P50/P95 单步延迟和缓存命中率。
- 确认不会使低成功率玩家“怎么都死不掉”。

## 10. 必须保留的约束

- 累计吻合度继续使用 Tester 的乘积公式。
- 不以速度决定比赛成绩。
- 玩家查询等待不计入操作倒计时。
- 普通移动保持单次请求/响应，不恢复第二次 ACK。
- 同一局必须可确定性复现；服务器仍是权威状态源。
- 不信任前端提交的成功率、出数或难度指标。
- 不改变房主承担自由对战查询费用的现有规则。
- 不因玩家自身次优选择而提供直接追赶补偿。
- 远程大表和本机云表必须走同一 selector 契约。
- 生产环境避免逐步写大段诊断日志；调试优先使用离线 fixture 和聚合统计。

## 11. 尚待决策的问题

1. 各 table family 的准确 layer 定义及统一获取接口。
2. profile 使用最优路线、真实玩家路线，还是两者混合。
3. 每个方向最多采样多少出生位置才能兼顾 P95 延迟。
4. 是否让相同步数的所有玩家严格共享 2/4 数值序列。
5. `spawn_adversity` 的目标分布和软上下限。
6. 当前 `1.15 / 1.20` 是保留为紧急上限、放宽，还是改成按 layer 分位控制。
7. decision ambiguity 与 mistake consequence 是否先保持双轴，还是需要一个初版组合分数。
8. 滑动窗口长度和难度债务衰减参数。
9. 查表未命中、剪枝值和成功率 0 应如何进入 profile，不能简单都视为同一种困难局面。

## 12. 给后续 agent 的工作原则

1. 开始实现前先阅读上述关键代码的最新版本，本文不是代码真相的替代品。
2. 先做可重复的离线样本和指标验证，不要直接在线上调整阈值。
3. 明确区分玩家决策难度、外生出数逆风、局面质量和局面罕见度。
4. 新算法必须能解释典型“赌 4 后成功率回升”案例。
5. 所有候选选择都必须有确定性测试，JS 不应复制权威随机逻辑。
6. 每次设计变化都同时评估公平性、自然死亡能力、查询放大倍数和单步 P95 延迟。
