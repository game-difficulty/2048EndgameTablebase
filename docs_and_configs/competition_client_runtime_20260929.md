# 比赛项目本机执行与轻量同步

日期：2026-09-29。状态：代码已实现，本地验证及线上部署完成。代码提交 `274af04`，发布版本 `20260929-client-runtime-r1`。

## 1. 职责划分

正式比赛统一使用 `client-runtime-v1`。项目 1–12 与练习页复用同一套 JavaScript 游戏引擎；项目 13–15 当前仍为纯练习项目，本来就在本地执行，本轮不改变项目池范围。

| 部分 | 负责内容 |
| --- | --- |
| 出战客户端 | 初始化棋盘、出数、移动、合并、特殊规则、撤销/重开、项目计时、达标/死亡/项目限时结束判定 |
| 本机 WASM Worker | 对抗出数；运算期间锁定该选手输入，超过 300ms 显示“思考中” |
| 比赛服务器 | 身份与阶段权限、提供共享种子、存储最新状态、转发公开画面、比较双方提交的成绩/用时、队伍总计时与比赛流程 |
| 对手/队友/直播端 | 展示最新公开状态，不再重演输入，也不自行计算对方出数 |

服务器不重放按键，不运行 Python 项目初始化、移动、死亡检测或 WASM。只保留简单结构/大小限制、上传者权限、项目实例和序号判断；不增加反作弊、随机序列保密或复杂结果验证。

## 2. 开局与随机数

双方出战者和队长就绪后仍自动开局。服务器建立双方独立 `instance_id`，通过出战者私有 `my_session.runtime` 下发：项目标识、冻结规则版本、同局相同种子、队伍剩余预算、恢复序号及 checkpoint。

客户端直接调用练习引擎建立初始状态，再异步上传第一帧。另一侧尚未载入时，比赛页显示“等待选手载入棋盘”，不伪造其棋盘。种子不再对出战者保密；普通公开画面仍不夹带 checkpoint / 撤销历史。

保持已有随机约定：

- 数字出数按有效步骤消费随机票据，无效方向不消费；撤销不回退随机状态。
- 初始出数、重开后的出数继续沿用引擎既定的票据消费规则。
- 真华容道形状、随机棋盘初始化、百步封锁各用独立的命名随机流，与普通出数相互隔离。
- 困难孤岛的生成概率使用当前出数票据。
- 骰子障碍使用含 `side` 的独立派生流，允许双方障碍不同，不扰动公共数字出数流。
- 对抗出数使用 WASM 的 seeded 接口。旧 WASM 不静默退回无种子计算；正式局计算失败恢复本步之前的状态和 RNG，提示重试。
- 兼容已冻结的旧版越来越大 4×4、随机形状 7×7 生成范围；当前 v3 分别为 4×5 和 6×6 生成范围后裁切。

## 3. 本地输入与上传完全分离

```text
方向键 / WASD / 滑动 / 方向按钮
                 ↓
       本机游戏引擎执行 → 立即更新自己的棋盘
                 ↓
       最新完整状态队列（独立于输入）
                 ↓
       HTTP 存储确认 → 异步广播公开状态
```

普通项目的 `move()` 同步返回，键盘、滑动和按钮不检查网络 `busy`。只有对抗出数的本地异步运算触发 `movePending`；滑动、合并、出现动画继续使用现有棋盘实现和时间参数。

上传使用 `LatestStateSender`：

- 每侧最多一个在途请求、一个待发送的最新完整快照。
- 正常按 100ms 间隔合并上传。合并的是网络快照，不是输入；所有有效本地操作照常执行。
- 在途请求期间发生的新操作替换待发送快照，不积压几十个过时请求。
- 完成成绩优先发送；在途请求结束后马上发送待发的最终状态。
- 请求 8 秒超时，失败后按 1 秒间隔重试最新状态。成功响应正文中断同样视为失败，不能当作收到确认。
- HTTP 在持久化后即可应答；广播放在响应后进行。广播并行向各端发送，慢连接有 2 秒发送超时，不拖住其他选手。

API：`POST /api/competitions/{code}/games/current/state`。

上传字段包括 `instance_id / sequence / phase_token / payload / checkpoint / result_value / elapsed_ms / finished / outcome`。公开 payload 维持原有三类棋盘协议，因此比赛页和直播渲染器不需要另写游戏引擎。

## 4. 顺序与接收端

- `sequence` 按状态变更递增，独立于 `moves`。撤销/重开可以减少步数，但不能减少 sequence。
- 服务器事务内按选手、实例检查序号；旧包和重复包不覆盖状态。
- 重复最终包仍返回当前比赛快照，处理“服务器已保存，但客户端丢失确认”的情况。
- 比赛页按实例与各侧 sequence 接收增量，不用黄方的新版本误杀白方另一条流的有效更新。
- 完整房间快照还有房间事件序号/version 防回退；直播还有 generation/content_sequence 防回退。
- 连续帧可播放原有移动动画；跳过中间帧时直接对齐新盘面，不拿不匹配的 `before` 播放动画。
- 自己的棋盘使用本地最新状态覆盖服务器镜像，旧回声不能把自己已走出的棋盘拉回去。

本协议按每名出战者一个操作端设计，不提供多个设备同时控制同一方的状态分支合并。换设备从服务器最近已保存的 checkpoint 恢复；未上传的本机进度不能凭空出现在另一台设备。

## 5. 计时与结算

项目计时使用 `performance.now()`，与服务端项目时钟基线对齐；UI 显示百分之一秒，提交用时精确到毫秒。重开和撤销不重置比赛用时。暂停通知会停止本地计时，恢复时继续；普通同步不能倒退正在运行的本地秒表。

普通计分项目：本地死亡后立即冻结自己用时和操作，异步提交最终成绩；双方均完成后服务器比较上传数值。骰子障碍上传盘面和，真华容道上传送出数量，其他计分项目上传得分。

竞速项目：

1. 本地达标立刻冻结时间，上传最终状态。
2. 服务器收到一方达标，通知另一方停止并提交最终状态。
3. 如果另一方在收到通知前也已经本地达标，保留其达标结果；双方均达标时比较本地用时，不按 HTTP 到达顺序判胜。
4. 尚未达标的一方提交 `opponent_finished`。通知后的收尾期限为 5 秒；对方长期离线时按其最后公开状态收尾，避免全场卡住。裁判暂停期间不执行这项收尾超时，恢复后重新给予 5 秒提交时间。
5. 允许重开的竞速项目死盘不作为比赛完成，可继续重开；允许撤销的项目仍可死盘后撤销。
6. 比赛结果页和直播结算展示竞速完成时间 / 未达标，而不是把合并得分作为竞速成绩展示。裁判修订仍保留修订结果。

真华容道的十分钟结束由本地 ticker 判定，即使不再输入也会完成并提交。

队伍 60 分钟包干仍由服务器管理。本地预算到零立即禁止继续移动/重开；服务端额外保留 5 秒成绩传输窗口，只接收预算内生成的结果，不增加可玩时间。完成后的队伍余额按上传完成用时扣减，不扣上传延迟。超出传输窗口的长断线不保证补报能改变已经结算的赛果，异常仍走裁判处理。

## 6. 恢复与异常

- 本机使用 sessionStorage 保存最新 packet，100ms 合并保存，离页时补存。
- 打开当前项目时比较本机缓存与服务端 checkpoint 的序号，使用较新的完整状态恢复。
- checkpoint 保存棋盘、特殊块、随机游标、必要计数、撤销历史；撤销历史使用紧凑数组，避免重复传输大量字段名。
- 网络故障显示重连提示但不阻塞本地操作；恢复后只上传最新状态。
- 阶段变化/裁判暂停重新获取当前房间状态；权限或非法状态等确定性错误停止重试并提示。
- 不承诺浏览器被强制结束、存储被清空或长时间断网时零数据损失；服务端只知道已收到的状态。
- 已确认不存在进行中的旧局，不保留服务端执行兼容分支。旧 `/move`、`/action` 接口已删除；移动、撤销、重开统一在本机执行，仅通过 `/state` 同步。项目限时结束也只接受本地判定，服务器不代算。

- `competition/shared/projectMetrics.mjs`：竞速赛果显示。
