# 直播房间、内容与礼物解耦

三局 AI 同屏的实施记录见 [live_three_ai_design.md](live_three_ai_design.md)。
该方案细化并替代下文多棋盘协议的初步 10 字节/步建议，单棋盘现有协议不变。

## 范围与边界

现有直播迁移到 `/rooms/ai-classic`，根地址和 `/api/live/*` 保留兼容。新 API 为
`/api/live/rooms/{room_id}/*`，未知房间返回 404，不能悄悄落到默认房间。
仅注册真实可用的房间，本次不创建虚假的真人/多 AI 直播。

`LivePage` 负责房间外壳：身份、聊天、点赞、在线观众、音乐、统计展示、连接生命周期。
`content/ClassicAiContent.vue` 拥有标题、说明、节点用时、棋盘/分数和历史三栏，组成一个矩形。
它负责快照、步进解码、棋盘动画和历史翻页。房间只把二进制帧和内容事件交给它，
不读取棋盘数组，不推演 2048，不依赖单个 AI 的 run 结构。
内容组件通过 `receive`、`resume` 接口接收数据，通过 `notice` 向外通知。
房间的 `RoomStage` 决定固定 16:9 外框，内容只能在内部适配，不改变长宽。
小窗入口、浏览器窗口和连接保活统一归房间管理；内容可选提供 `getPipFrame` 供视频模式绘制。
Document PiP 直接使用既有舞台。详见 [房间小窗方案](live_room_pip_design.md)。
标题与文案由房间注册信息提供。内容组件、协议和房间生命周期分别注册与管理。

同一房间只使用一个有序 WebSocket，房间 ID 在 URL/握手里传一次，不逐步重传。
前端按组件实例注入房间 API，不能用可变全局 roomId；以后多实例同时挂载时不互相污染。
路由切换重建房间实例，关闭旧连接、清理定时器和动画，旧异步结果不得覆盖新房间。

## 房间与数据隔离

每个房间一个内存 hub（观众、聊天、队列、限流、主播锁）及内容存储；默认房间继续使用
原 `LIVE_DB_PATH`，其余房间使用相邻独立 SQLite 文件。账户/钱包仍共用认证数据库。
观众贡献按房间隔离；红包队列、福袋和礼物 outbox 必须按房间/赠送目标查询。
注册表控制内容类型、发布凭据和活动能力。新房间不可自动继承默认主播凭据。
已有管理页仍控制默认 AI 房间；未来房间管理应显式传 room_id。

## 礼物模块

前端通用礼物组件、素材、价格与重试客户端归入 `features/gifts`；通过 provider 注入
API base 与目标，不依赖直播棋盘。红包入口使用插槽/开关，未来对战页可不提供它。
后端订单服务归入 `backend/gifts`，接受由宿主验证的目标（如 `live:ai-classic`，未来
`battle:<match>:<recipient>`），不直接查询直播是否在线；宿主提供是否允许赠送。

同一 UUID 只能对应同一用户、目标和报价。目标加入订单/回执/账本与事件；连击只在同一
目标内合并，outbox 投递只送对应房间。原有订单通过增量 schema 迁移归到默认房间，保留
原 fingerprint，使旧订单的不确定重试仍可恢复。每日预算与余额全站共享，换房不重置。
对战接入时，服务端须验证比赛、观众资格与接收者，禁止直接信任客户端任意 target。

## 带宽与恢复

现有 `classic-step-v1` 保持 uint32 seq + uint32 delta_ms + uint8 move，9 字节/步。
12.5 步/秒是 112.5 字节/秒/观众的应用层步进负载（约 0.405 MB/小时），不含 JSON、
WebSocket/TLS/TCP、CDN计费开销。不会转视频、重复发送整盘或每步回执。
只在首次接入、重新开局、重连/慢消费者恢复时发快照；序号异常关闭后重连，不能静默丢步。
房间元数据和协议版本放在首次发现/快照中，不添加到每个二进制帧。

未来真人经典规则可复用该协议与渲染器（服务端须验证操作及授权）；多棋盘建议新建
`classic-multi-v1`，以 1 字节 lane + 现有 9 字节步进 = 10 字节/步，快照含 lane、
run_id、seq、board。每 lane 独立序号，合并为一个房间连接。先不要上线没有生产者的协议。
N 个棋盘的负载与总步数成正比。只有需要压低传输包数量时再实测 40–80ms 批量窗口；
应用字节与真实出口带宽要分别测量，不能把理论值当成云账单承诺。

保留 32 条发送队列、5 秒发送超时、过载快照恢复、隐藏页既有三分钟宽限及 PiP 策略。
配置仍为单后端 worker；若以后横向扩容，需要房间归属路由/消息总线，不能直接开多 worker。

## 研究依据与验证

- Vue 实例级依赖注入：https://vuejs.org/guide/components/provide-inject.html
- WebSocket 没有自动背压：https://developer.mozilla.org/en-US/docs/Web/API/WebSocket
- Nginx 需要为 WebSocket 显式转发 Upgrade：https://nginx.org/en/docs/http/websocket.html

验证包括：旧 API 兼容、房间发现/未知 ID、两房间状态与广播隔离、发布凭据隔离、9 字节帧、
礼物跨目标重试/连击/预算/outbox、红包福袋隔离、原有直播测试、前端构建和浏览器视觉检查。
部署必须同时更新后端、完整静态构建和 Nginx 房间深链/WebSocket 规则；先备份数据与旧版本。

## 实施结果与扩展步骤

已实现以上默认房间迁移、实例级前端上下文、后端房间注册表、内容适配器、共享礼物核心、
订单/事件目标隔离、红包/福袋/贡献榜房间隔离、Nginx 规则与 Vite 深链支持。
旧导入路径保留轻量转发，避免把两套逻辑留在工程里。旧直播发布者仍可用 `/api/live/publish`。

新增房间时，在 `backend/live/rooms.py` 注册 `RoomDefinition`，使用独立的
`publish_token_env`，默认 `milestone_rewards=False`，不能自动继承平台出资福袋。
`/api/live/rooms` 返回公开目录（不返回发布密钥）；`/api/live/rooms/{id}` 返回房间描述。
同一种内容可被多个房间复用。不同协议则须同时注册前后端适配器，未识别的协议不会回退解码。

前端内容协议：接收 `lang`、`streamState` 属性，注入 `useRoom()` 获取不可变房间描述及 API；
暴露 `receive(ArrayBuffer | JSON)`、`resume()`，发出 `notice`、`pip-active` 事件。
`receive` 遇到非法或断序数据应抛错，由房间关闭连接并重新获取快照。
历史 HTTP 响应仅更新摘要，不得覆盖已经由 WebSocket 推进的实时棋盘。

后端适配器由 `content.py` 的 `CONTENT_FACTORIES[(kind, protocol)]` 创建，提供
`start()`、`save()`、`snapshot()`、`publish(ws, hub)`、`run_id`、`reached_milestones()`，
以及符合房间摘要/历史/回放/管理接口的 `store`。`LiveHub.run` 仅保留为旧管理/测试兼容属性；
房间运行逻辑通过适配器读取内容，不依赖棋盘和步进编码。未来多棋盘内容可定义自己的复合
快照、记录和摘要，但保持房间统计输出约定。

对战前端可通过 `provideGiftClient(createGiftClient({base, target}))` 挂载 `GiftPanel`
与 `GiftEffects`，宿主监听实时礼物事件交给特效组件。礼物面板的红包入口由属性开关控制。
`backend/gifts/service.py` 处理扣费及 outbox，宿主把通过验证的 `target` 和可赠送状态传入，
如有贡献榜在同一事务内通过 `on_paid(db, uid, cost)` 回调记账。
钱包/每日预算是共享的，订单恢复查询只允许当前目标；浏览器未确认订单按目标保存。

本次没有创建正式真人/多 AI 房间，没有新增视频传输，也没有开放任意用户自行注册房间。
本地 QA 临时注册了第二个 AI 房间验证隔离，该房间不在生产注册表中。

## 发布与回退注意

先停止旧后端写入，在同一维护窗口更新后端与完整静态构建，并更新 live Nginx 配置、
通过 `nginx -t` 后重载。新后端首次启动执行增量 schema 迁移，旧礼物与活动归到默认房间。
不要一边运行旧订单写入代码一边迁移：旧版本用无列名 INSERT，新增列后不兼容。
上线后的回退优先保留新后端、回退前端（旧 API 仍可用）；如必须回退后端，应先给旧版
订单 INSERT 补齐显式列名，并保留目标隔离迁移。已产生新账单后不能直接恢复整份认证库备份，
否则会丢失上线期间的正常交易。房间 SQLite 与认证库应使用 SQLite 在线备份工具做一致备份。
