# 近 168 小时榜与每周 Token 结算设计

状态：本地实现，未部署。适用于主站游戏页普通／对抗榜与对局站四种变体。仅这六个分数榜调整为滚动窗口；Token 消耗榜、总榜不受影响。

## 口径和页面

- 页面“周榜”改名为“近 7 天 / Last 7 days”。任一读取时刻 `T`，仅纳入服务器认可的成绩时间落在 `[T - 168 小时, T)` 的合格对局。同一账号、同一榜只取窗口内最佳对局；分数相同时保留较早达成的对局，再以稳定 ID 断开完全相同的排序。
- 页面不定时轮询。进入页面、切换榜、用户主动刷新及本站对局通过验证后才请求。页面侧栏读取前 10 条，完整榜单按需读取前 100 条；两者来自同一份后端快照，避免两个排序口径。公开 API 只返回头像／用户名／分数／棋块／时间／回放标识等摘要，不读取回放 BLOB。
- 前端显示榜与奖励结算榜的用途不同：滚动榜随时间变化；每周 Token 名次由固定时间的冻结快照决定。页面应单独说明结算时点与规则。主站周榜的“查看完整榜单”应传递当前周榜键，不能跳到总榜。
- 分数依据已验证的服务器时间。主站使用提交时间 `submitted_at`，且只在验证成功后入候选；对局站原生局使用服务器封存／最后有效批次时间；Verse 导入使用外站原始对局时间，不用导入时间。导入和人工审核的资格生效时间单独记录；后续批准不得悄悄改写已经冻结的奖励榜。

## 为何不能只存 TOP10

一条 TOP10 成绩过期时，第 11 名甚至同一玩家较新的次佳成绩可能补位。只保存 TOP10 会丢失这些候选。对局站完整榜单目前还提供前 100 名。因此至少要保留窗口内可递补的窄摘要，并物化每人当前最佳和前 100 名。

## 维护结构

每个站点分别维护三层小数据，按现有数据库归属存放：

1. `rolling_candidates`：每条已验证、可公开且时间可能进入窗口的对局一行。包含榜键、账号 ID、对局／回放 ID、分数、最大棋块、被认可的成绩时间、资格与生效时间，以及少量展示字段；不包含回放 BLOB 或完整棋盘状态。`rolling_candidate_periods` 留存资格生效与撤销时间。索引 `(board, user_id, score DESC, achieved_at ASC, run_id)` 与 `(board, achieved_at)`。对局站已有完整 `human_runs`，但读榜使用独立窄表，避免每次解析 `state` JSON 和触及归档页。
2. `rolling_player_best`：每个榜、每个账号一行当前 168 小时最佳。索引 `(board, score DESC, achieved_at ASC, user_id)`，另索引成绩到期时刻。某个最佳过期时，用候选表的用户索引找次佳；非最佳候选过期可批量清理。
3. `rolling_board_entries`：每榜物化前 100 名，附版本号和最近一条相关到期时间。侧栏读前 10，完整榜读前 100。替换时只在排名真正变化时写入，避免每局重写 100 行。

新成绩通过完整验证／封存后，在原业务提交成功时插入候选并更新该玩家最佳；只在可能改变前 100 或替换当前入榜记录时重排榜单。审核批准／撤销、外站归属确认／撤销、隐藏资格变化、账号停用等也按同一事件更新。回放补全只更新回放可用性，不改变名次。可以在后续优化中丢弃同一玩家被较晚且不低分的对局永久支配的候选，但不能丢弃高分过期后可能递补的较新低分局。

到期采用后台到期任务加读取兜底：后台按最早到期时刻批量处理过期最佳，找同玩家次佳，并从最佳表的有序索引取前 100；读接口仅比较 `next_expiry_at`，若后台迟到，由单个请求抢锁补做一次到期维护，其余请求等待该次维护。不会在每次 GET 扫描、分组或排序全部历史。服务重启后通过数据库中的到期时刻恢复。到期处理、候选状态与快照版本要以短事务原子提交；并发验证和到期维护须以同一榜锁／事务序列化。可周期审计重建结果，但审计不在读路径。

主站目前 `gamer_weekly_high_scores` 是自然周每人最佳，且被 Token 奖励结算直接读取；它无法表示跨自然周的 168 小时窗口，也无法递补同一玩家较新的次佳局。滚动榜另建上述摘要，不能直接改原表的含义。主站若要求滚动榜回放始终可看，需要为所有可能递补的候选保留对应压缩回放至该局过期或其奖励结算完毕；现有只保留总榜／自然周 PB 回放的策略不够。回放应按对局 ID 引用并避免在多张成绩表中重复存相同 BLOB。

新验证的主站对局把回放压缩一次存于 `gamer_rolling_replays`；总榜／旧自然周表保留回放 ID 与成绩摘要，`record_blob` 留空。读取旧记录仍兼容旧表里的原始回放。压缩回放须保留到该候选既不在滚动窗口、结算已完成，且不再被总榜或旧自然周表引用；归档页和回放接口按 ID 解压读取。

旧自然周表只继续收录最后一个需结算的旧周期；切换后不再为新自然周写入成绩。这样旧表可以正常清理，且不会因永远等不到旧规则结算而无限增长。

## 每周一北京时间 08:00 的奖励

- 结算边界 `C` 是周一 `Asia/Shanghai` 08:00，即周一 00:00 UTC。每次冻结六个分数榜在 `[C - 168 小时, C)` 中的成绩：主站两榜各前五名，对局站四榜各前十名，并保存账号、对局 ID、分数、成绩时间、排序席位与规则版本。下一结算周期从 `C` 开始；边界上的对局只属于下一周期。
- 奖励直接依据这份不可变快照，不依据发奖时的实时榜。因此任务晚几分钟运行、重试或服务器重启不会改变获奖名单。主站延迟验证的提交仍按其服务器提交时间归属；若截止前已有待验证提交，先等待验证／明确过期，再生成快照。对局站导入须在截止前完成归属核验并具备入榜资格；原始局时间虽在窗口内、但截止后才导入／批准的记录不追溯本期奖励。作弊撤销在结算前阻止发奖；结算后的撤销另留审核／追回记录，不能静默改写已发账本。
- 六榜分别结算，可允许同一账号在不同榜获奖。每榜按分数高、成绩时间早、稳定账号／对局 ID 顺序取奖励席位。展示仍可显示同分并列名次，奖励按稳定排序的席位发放。主站普通榜第 1–5 名 `10000/8000/5000/3000/2000`，对抗榜 `5000/4000/3000/2000/1000`。对局站 4×4 第 1–10 名 `36000/24000/16000/12000/10000/8000/6000/5000/4000/3000`；3×4、3×3、2×4 各榜第 1–10 名 `16000/12000/10000/8000/6000/5000/4000/3000/2000/1000`。
- 结算任务在 08:00 触发，并保留定期补偿扫描，服务中断后从未结算的边界补跑。SQLite 中保存冻结快照、结算状态和每笔奖励凭证；发奖只在账号／Token 数据库的短事务中进行，幂等键包含站点、榜、结算边界及奖励席位。复用现有 `token_reward_receipts`、`token_ledger` 和 `_credit` 的一次入账语义，不依赖进程内锁保证幂等。对局站数据在另一 SQLite 文件中，先持久化不可变结算输入，再由账号库幂等支付；不持有两个数据库的长写事务。
- 切换现有主站自然周奖励时，应设置明确的生效边界与规则版本，保留已经支付的旧周账本；新规则只对切换后完整的一个 168 小时结算窗口生效，避免双发或跨规则重算。

本地实现使用 `token_reward_state.rolling_first_boundary` 持久化首个新规则结算边界，至少留出一整个 168 小时窗口；自然周旧结算在新窗口起点前停止。切换时旧自然周于周一 00:00 结束，而新窗口从周一 08:00 开始，两者之间有一次性的 8 小时空档，需要上线前决定是否单独补偿。不能通过重算旧自然周与新榜重叠发奖。

## 验收重点

固定时钟验证跨周、闰日与周一 07:59:59／08:00:00；榜首过期后同人次佳和其他玩家递补；第 10／11、100／101 名递补；成绩同分；新局、手动审核撤销、Verse 归属变动；延迟验证；服务器重启后的到期补偿；多进程同时请求与重复结算只发一笔；外站原始时间和资格生效时间分别生效。性能验收检查页面 GET 只读小快照、无历史排序及无回放 BLOB，事件维护的 SQLite 写锁时间和候选／回放存储增长。
