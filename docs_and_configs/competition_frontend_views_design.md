# 独立比赛系统前端视图与关键交互设计

状态：设计草案，未实施  
更新时间：2026-09-27  
关联文档：`competition_backend_design.md`

## 1. 文档目的与范围

本文把独立比赛系统的后端状态机映射为前端窗口、角色视角和关键交互。

本文覆盖：

- 举办方、裁判、队长、队员、当前出战选手和观众分别需要哪些窗口；
- 候场、准备、抽签、BP、盲选、布阵、项目对局、局间确认和全场结算的页面结构；
- 每个窗口显示哪些组件、组件放置位置和主次层级；
- 关键操作如何确认、锁定、失败和恢复；
- 比赛控制页与现有 Live 观众页的职责边界；
- 桌面端信息架构、可访问性和异常状态。

本文不覆盖：

- 具体项目规则及项目专属画面；
- 最终品牌视觉、插画、动效素材和精确色值；
- 移动端完整比赛操作；
- 前端组件代码和路由实现。

## 2. 联网调研结论

本设计参考了 KPL、VALORANT、League of Legends、Dota 2 等赛事的 BP、比赛控制和转播模式，
但不复制任何单一产品的外观。

### 2.1 成熟赛事的共同模式

1. **双方镜像，公共信息居中**

   BP 和赛中画面通常把两队放在左右两侧，中央只承载公共项目、当前阶段和系列比分。
   这种布局让阵营归属无需反复阅读标签，也适合黄/白双方固定映射。

2. **选择历史常驻，不用弹窗替代主界面**

   已选、已 BAN 和待选槽位在 BP 全程保留。倒计时、当前行动方和锁定结果共同构成主视觉，
   而不是每一步弹出一个模态窗口。

3. **队伍可以讨论，只有队长锁定**

   VALORANT Premier 的地图选择允许全队投票，但由 party leader 锁定最终选择。这印证了“队员可看、
   可表达建议；队长拥有唯一提交权”的角色分层。首版可以不实现投票，但界面必须明确队长才可锁定。

4. **双方准备，裁判最终放行**

   League of Legends 赛事规则要求所有选手到位、双方确认准备后，由裁判或官方人员指示开始。
   暂停后的恢复同样由双方队长确认、裁判执行。这比任一选手直接启动或恢复更适合正式比赛。

5. **裁判工作区与比赛画面分离**

   成熟赛事管理工具通常把 Games、Lineups、Settings 和事件记录分为独立工作区。裁判需要的是
   高密度状态、异常和审计，不应在选手比赛画面上叠一排危险按钮。

6. **转播画面使用固定、可长期扩展的外壳**

   VCT 等赛事把转播视觉做成可适配不同地区和阶段的系统工具。对本项目而言，稳定的队伍、比分、
   时钟和 A/B/C 外壳应与未来项目专属渲染器分开。

7. **暂停是受控流程，不是普通按钮**

   正式比赛中，选手通常报告问题，裁判决定是否暂停；恢复由裁判在双方就绪后执行。暂停期间应限制
   额外交流，避免暂停成为战术时间。

## 3. 设计原则

### 3.1 一个角色只有一个明确主任务

- 举办方：配置和监督赛事；
- 裁判：确认比赛可继续、处理异常；
- 队长：准备、BP、布阵和结果确认；
- 队员：落座、检查设备、等待出战；
- 当前出战选手：完成当前项目；
- 观众：理解比赛进度和观看公开内容。

不要因为用户同时拥有多个权限，就把所有操作同时展示。界面默认显示当前阶段最相关的工作区，
其他能力进入明确的管理页或裁判抽屉。

### 3.2 黄方始终在左，白方始终在右

比赛站和 Live 站都固定：

- 黄方：左侧；
- 白方：右侧；
- 公共状态：中央；
- 当前行动方：除颜色外，还用“你的回合”、箭头和倒计时标签表示。

不能依赖黄/白颜色单独传递含义。

### 3.3 阶段比页面更重要

选手端使用一个比赛房间壳，根据服务器 phase 更换主舞台。刷新后直接恢复当前阶段，
不要求用户重新经过历史页面。

### 3.4 秘密信息在组件树入口前裁剪

前端不接收无权查看的 X/Y、对方布阵或裁判备注。不能用 `v-if`、透明度或遮罩隐藏已经到达浏览器的数据。

### 3.5 单一高强调操作

每个阶段最多一个高强调按钮，例如：

- “占据此席位”；
- “队长准备”；
- “锁定选择与 BAN”；
- “提交布阵”；
- “确认本局结果”。

取消、返回和报告问题保持次级。裁判危险操作不能与普通推进按钮同级。

### 3.6 服务器事实优先

- 倒计时使用 `server_time + deadline_at`；
- 操作提交后先显示“正在确认”，收到服务端接受后才进入锁定态；
- 网络失败不假装成功；
- 自动选择、超时和裁判操作都显示来源。

## 5. 全局比赛房间壳

选手端 P1–P12 共用同一个页面壳，避免每个阶段重新学习导航。

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 赛事名 / 房间码      阶段标签 + 服务器状态        网络状态  帮助  账号 │ 64
├──────────────────────────────────────────────────────────────────────────┤
│ 黄方  剩余时间             A · B · C 赛程条             剩余时间  白方 │ 76
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│                         当前阶段主舞台                                   │
│                                                                          │
├──────────────────────────────────────────────────────────────────────────┤
│ 当前身份 / 席位      阶段说明或错误提示                 报告问题 / 主操作│ 72
└──────────────────────────────────────────────────────────────────────────┘
```

### 5.1 顶部第一行

左侧：

- 赛事名；
- 房间码；
- 是否正式比赛；
- 裁判在线状态。

中间：

- 当前 phase 的人类可读名称；
- `LIVE / PAUSED / RECONNECTING`；
- 当前阶段截止时间。

右侧：

- 网络状态；
- 规则帮助；
- 当前账号。

### 5.2 赛程状态条

全程显示三个项目槽位：

```text
[A 待定/项目名/比分] ─ [B 待定/项目名/比分] ─ [C 待定/项目名/比分]
```

BP 前显示空槽；揭晓后逐步填充；进行中的一局突出；已结束显示胜方和完成原因。

黄白两队包干时钟在同一行两端，始终固定位置，避免局间页面切换后用户寻找时间。

### 5.3 底部操作条

底部只放本角色当前可执行操作：

- 左：当前身份、席位、队长标识；
- 中：系统说明、冲突或自动选择提示；
- 右：报告问题、次级操作、唯一主操作。

## 6. 举办方窗口

### 6.1 O1 比赛创建与配置

使用三步式页面，不使用一个超长表单。

```text
步骤 1 基础信息  →  步骤 2 队伍与权限  →  步骤 3 项目池与规则确认
```

#### 步骤 1：基础信息

左侧主表单：

- 赛事；
- 比赛名称；
- 黄方队名；
- 白方队名；
- 计划开始时间；
- 房间可见性；
- 每队包干时长。

右侧摘要：

- 房间创建后会生成什么；
- 选手人数；
- A/B/C流程；
- Live 是否自动开放。

#### 步骤 2：权限

- 举办方列表；
- 裁判列表；
- 每个裁判的权限范围；
- 是否允许举办方执行裁判操作。

#### 步骤 3：项目池

本阶段只设计容器，不规定项目规则：

- 项目池选择；
- 规则版本；
- 排序预览；
- 最低项目数量校验；
- 布阵公开策略；
- Live 开始和结束策略。

页面底部固定显示“创建草稿”和“创建并开放”，后者需要最终确认摘要。

### 6.2 O2 比赛总览列表

数据表而不是卡片墙：

| 比赛 | 对阵 | 阶段 | 裁判 | 六席 | 当前项目 | 异常 | 更新时间 |

顶部过滤：进行中、等待、需处理、已结束。默认把“需处理”放在最前，不依赖红色闪烁吸引注意。

点击一行进入 R1 裁判控制台。

## 7. 裁判窗口

### 7.1 R1 单场裁判控制台

裁判窗口与选手窗口完全分离，使用高密度桌面布局。

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 比赛 / 对阵 / phase / revision / Live状态       [暂停] [更多裁判操作]  │
├───────────────┬───────────────────────────────────────┬──────────────────┤
│ 双方阵容       │ 当前阶段工作区                        │ 风险与操作       │
│ 在线/掉线      │ Games / Draft / Lineups / Clocks     │ 允许的下一步     │
│ 队长准备       │ 当前权威状态与公开投影预览            │ 问题报告         │
│ 当前出战者     │                                       │ 裁判备注         │
├───────────────┴───────────────────────────────────────┴──────────────────┤
│ 有序事件日志：时间 / 操作者 / 事件 / revision / request id             │
└──────────────────────────────────────────────────────────────────────────┘
```

#### 左栏：人员状态

- 黄1/2/3、白1/2/3；
- 账号、席位、在线状态；
- 当前设备连接；
- 队长准备；
- 当前出战者；
- 项目实例连接状态。

#### 中栏：阶段工作区

顶部标签：

- `Games`：A/B/C 状态和结果；
- `Draft`：抽签、选/BAN、盲选密封与揭晓；
- `Lineups`：双方提交状态和允许查看的密封阵容；
- `Clocks`：剩余时间、运行原因、最近启停事件；
- `Settings`：冻结配置，只读为主。

默认标签跟随当前阶段，但裁判可以查看其他标签。

#### 右栏：裁判动作

普通动作：

- 请求双方重新确认；
- 标记问题已解决；
- 开始下一局；
- 恢复比赛。

危险动作进入“更多裁判操作”抽屉：

- 强制替换席位；
- 回滚当前阶段；
- 强制默认选择；
- 判负或改判；
- 取消比赛。

危险操作必须填写原因、二次确认，并在确认页显示会失效的准备、BP、布阵或结果。

#### 底部事件日志

- 默认显示最近事件；
- 重要事件可按类型过滤；
- 每条包含服务器时间、操作者、公开摘要和 revision；
- 秘密内容不直接在列表明文展示；
- 裁判点击后才在受控详情中查看。

## 8. 选手候场与准备

### 8.1 P1 候场与落座

```text
┌──────────────────黄方──────────────────┬───────────────白方──────────────────┐
│ [黄1 队长席]                           │                           [白1 队长席]│
│ [黄2 队员席]                           │                           [白2 队员席]│
│ [黄3 队员席]                           │                           [白3 队员席]│
└────────────────────────────────────────┴─────────────────────────────────────┘
                         房间规则摘要 / 裁判状态
```

席位卡包含：

- 头像、昵称；
- 1/2/3号位；
- 队长标识；
- 在线/暂离；
- “你”的标识；
- 空位上的“选择此席位”。

交互：

- 点击空位后，在底部操作条显示即将加入的队伍和席位；
- 点击“占据此席位”后进入 pending，收到服务器确认才显示本人头像；
- 并发抢座失败时保持原状态并提示“该席位刚刚被占用”；
- 已落座用户换座时采用一次原子命令，不先清空原席位；
- 进入 READY 后普通换座入口消失。

### 8.2 P2 双队长准备与技术检查

六席满后，席位布局保持不变，中央出现技术检查单：

- 六名选手是否在线；
- 当前浏览器是否获得操作焦点；
- 项目运行器连通性；
- 规则确认；
- 裁判在线。

队长区域显示：

```text
黄队长：[未准备 / 已准备]
白队长：[未准备 / 已准备]
裁判：  [等待双方 / 可以开始]
```

队长可以在对方未准备前取消。双方都准备后进入短暂锁定态，由裁判或自动规则放行；
不能让第二位队长的点击直接绕过裁判配置。

## 9. 抽签与 BP

### 9.1 P3 抽签揭晓

抽签是短暂全屏阶段，不提供操作：

- 左右显示队伍；
- 中央显示“先手抽签”；
- 动画只负责展示，结果由服务器快照决定；
- 最终停留 2–3 秒，明确显示“黄方先手”或“白方先手”；
- 刷新或减少动态效果时直接显示结果，不重播长动画。

抽签结果下方提供审计标识，例如“服务器抽签 · 赛后可验证”，不展示种子。

### 9.2 P4 先后手选择与 BAN

```text
┌──────黄方 280──────┬────────────项目池 / 主要区域────────────┬──────白方 280──────┐
│ 队长与队员          │ 阶段：先手选择                           │          队长与队员 │
│ A [待选/已选]       │           00:43                          │       [待选/已选] B │
│ BAN M [待定]        │ 项目卡片矩阵                              │        [待定] BAN N │
│ 私有操作摘要        │ 可选 / 已选 / 已BAN / 不可用              │        私有操作摘要 │
├─────────────────────┴──────────────────────────────────────────┴──────────────────┤
│ 公共进程：抽签 ✓  →  A/M 当前  →  B/N  →  盲选  →  C揭晓                    │
└──────────────────────────────────────────────────────────────────────────────────┘
```

#### 中央项目池

每张项目卡只显示决策所需内容：

- 封面或识别图；
- 项目名；
- 一句话规则摘要；
- 规则版本或难度；
- 状态：可选、当前预选、已选、已 BAN、不可用。

详情通过固定侧栏或项目池上方的信息区展示，不能让悬停成为唯一查看方式。

#### 当前队长操作

先点击一个项目放入“选择”槽，再点击另一个项目放入“BAN”槽。也可先选槽位再选项目。

底部操作区显示：

```text
本轮选择：项目 A     本轮 BAN：项目 M     [清除] [锁定选择与 BAN]
```

必须两槽都合法后才能锁定。锁定前可修改；锁定后普通用户不可撤回。

#### 非当前队长和队员

- 项目池可查看但不可操作；
- 明确显示“等待黄方队长”而不是禁用按钮堆；
- 队员可拥有非绑定的“建议”能力作为后续选项，但首版不要求实现；
- 对方正在预选的内容不可见，只在锁定后公开。

#### 倒计时

- 60 秒只突出当前行动队伍；
- 10 秒内进入紧急态；
- 到 0 后进入“系统选择中”，随后展示自动结果；
- 自动结果标注“超时自动选择”；
- 客户端不得自行在 0 秒选中第一项。

### 9.3 P5 双方盲选

布局延续 BP 页面，中央项目池不变，左右各出现一个盲选槽。

队长自己的页面：

- 看见自己的预选项目；
- 对方槽位显示“未提交/已密封”；
- 点击“提交盲选”后自己的项目仍可见但不可修改；
- 等待期间显示提交时间和密封状态。

队员页面：

- 不显示双方具体 X/Y；
- 只显示本队是否提交和对方是否提交；
- 是否允许看到本队队长的盲选由规则决定，默认不显示以减少泄露面。

裁判页面：

- 默认也显示密封状态；
- 如规则允许查看，必须通过受控操作打开并写审计。

双方提交后进入统一揭晓画面：

```text
黄方 X  ──────┐
               ├─ 系统确定 C ─→ 项目 C
白方 Y  ──────┘
```

X=Y时直接显示“一致选择”，不播放伪随机二选一。

## 10. 秘密布阵

### 10.1 P6 队长布阵视图

```text
┌────本队选手────┬────────────A / B / C 出战槽────────────┬────对方状态────┐
│ 1号位 队长      │ A [选择选手]  项目名称                 │ A 已密封/等待   │
│ 2号位 队员      │ B [选择选手]  项目名称                 │ B 已密封/等待   │
│ 3号位 队员      │ C [选择选手]  项目名称                 │ C 已密封/等待   │
│ 03:00           │             [提交布阵]                 │ 对方不可见      │
└─────────────────┴────────────────────────────────────────┴────────────────┘
```

交互同时支持：

- 拖拽选手到 A/B/C；
- 先点选手再点项目槽；
- 项目槽下拉选择。

拖拽不能是唯一交互方式。

规则校验实时显示：

- 每位选手只出现一次；
- 三个项目都已安排；
- 当前席位 revision 未改变。

点击“提交布阵”后显示简短确认摘要。由于布阵只有一次、时限较长且提交后不可逆，这里允许使用确认层。

### 10.2 队员视图

队员只看到：

- A/B/C项目；
- 本队队长是否已提交；
- 提交前显示“等待队长安排”；
- 本队提交后可查看本队完整 A/B/C 编排，不能查看对方编排。

队员不能通过 DOM、网络响应或预加载资源推断对方布阵。

## 11. 开局检查与项目对局

### 11.1 P7 开局检查

每局正式计时前显示短暂检查页：

- 当前项目 A/B/C；
- 黄白出战者；
- 双方项目实例连接状态；
- 两队剩余总时间；
- 当前出战者“已就绪”；
- 队长确认；
- 裁判开始。

正常情况下该页快速通过；发生运行器或连接故障时，它成为安全停靠点，不能先启动总时钟再等待初始化。

### 11.2 P8 当前出战选手操作台

项目规则未知，因此采用稳定外壳 + 项目插槽：

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 黄方 1              项目 A · 项目名称               白方 0          │
│ 队伍剩余 48:26                                  对方剩余 51:03      │
├──────────────────────────────┬───────────────────────────────────────┤
│                              │ 项目目标 / 规则摘要                    │
│ 黄方 Project Public View     │ 白方 Project Public View               │
│ 当前出战者可操作              │ 当前出战者可操作                        │
│                              │ 连接与校验状态                         │
│                              │                                       │
├──────────────────────────────┴───────────────────────────────────────┤
│ 输入提示 / 系统消息                         [报告问题]               │
└──────────────────────────────────────────────────────────────────────┘
```

原则：

- 双方项目公开画面等权占据主要区域；
- 所有六名参赛选手均可实时查看黄、白双方的公开棋盘、得分与进度；这与 Battle 的对手信息隔离规则不同；
- 只有当前场次的出战者能操作自己的棋盘，查看权不赋予操作权；
- 总时钟固定在顶部；
- 项目自己的局内计时、目标和特殊控件放在 Project Player View 内；
- 普通项目完成按钮不能绕过项目运行器判定；
- 页面离开需要明确警告，但关闭页面不会暂停队伍时钟。

### 11.3 P9 队长和未出战队员视图

队长和未出战队员可以查看双方项目运行器发布的公开画面。默认显示：

- 当前项目；
- 本队出战者和连接状态；
- 双方队伍总时钟；
- 双方实时公开棋盘、得分、步数以及“进行中/已完成”状态；
- A/B/C系列比分；
- 报告问题入口。

项目运行器未列入公开协议的内部状态、控制令牌和校验数据仍不得下发。公开画面由后端
Projection 明确生成，不能把完整私有状态交给前端后再隐藏。

### 11.4 一方先完成

已完成方的出战选手看到：

- “服务器已接受完成”；
- 本队时钟已暂停；
- “等待对方结束”；
- 自己的项目摘要；
- 禁止继续输入。

另一方继续比赛时仍可看到已完成方冻结的公开棋盘和得分，但结果阶段开始前不显示系统判定的胜负。

## 12. 单局结果与确认

### 12.1 P10 结果确认

双方都结束后显示对称结果页：

```text
┌────────────黄方结果────────────┬────项目 A 结果────┬────────────白方结果────────────┐
│ 选手 / 公开指标 / 完成原因      │  胜方 / 平局       │      完成原因 / 公开指标 / 选手 │
│ 本队剩余时间                    │  当前系列比分       │                    剩余时间 本队 │
└─────────────────────────────────┴────────────────────┴─────────────────────────────────┘
             黄队长 已确认 / 未确认       白队长 已确认 / 未确认
```

队长按钮：

- “确认结果”；
- “报告结果问题”。

确认动作绑定 `result_revision`。裁判改判后旧确认自动清除，页面必须明确提示“结果已更新，请重新确认”。

两位队长确认后，裁判或自动规则推进下一局。按钮文案不能让队长误以为自己单方面启动下一局。

## 13. 暂停、断线和争议

### 13.1 P11 选手问题报告

选手不直接拥有“暂停比赛”按钮，而是“报告问题”。点击后选择：

- 网络或设备；
- 项目异常；
- 规则疑问；
- 其他。

提交后：

- 裁判控制台出现高优先级问题；
- 页面显示已报告及时间；
- 比赛是否暂停仍以服务器状态为准；
- 重复点击不会产生多条相同问题。

### 13.2 暂停覆盖层

比赛暂停时所有参与者看到不可绕过的覆盖层：

- “比赛已暂停”；
- 公开原因；
- 暂停发起者；
- 两队时钟已停止；
- 当前恢复准备状态；
- “等待裁判恢复”。

队长可点击“本队已准备恢复”，裁判在双方准备后点击“恢复比赛”。队员不能恢复。

### 13.3 断线

- 顶部网络状态立即变为“正在重连”；
- 主操作锁定；
- 页面保留最后确认状态，但明确标记可能过期；
- 重连后用完整快照替换，不补播会阻止操作的长动画；
- 若服务器阶段已推进，直接进入新阶段；
- 不能因为本地倒计时到 0 自行推进。

## 14. 全场结算

### 14.1 P12 选手结算页

首屏：

- 胜方队伍；
- 总比分；
- 黄白剩余时间；
- A/B/C逐局胜方；
- 比赛结束原因。

第二层：

- 每局项目、出战者、公开成绩；
- 超时、判罚或改判标记；
- 回放状态；
- 审计编号。

操作：

- 查看比赛详情；
- 打开公开直播回放；
- 离开房间。

正式结果冻结前显示“裁判结算中”，不能提前展示最终胜者动画。

## 15. Live 比赛内容 L1

观众继续使用现有 LivePage。聊天、点赞、在线人数、音乐和画中画位于既有房间外壳，
本节只设计 1280×720 `CompetitionMatchContent` 内部。

### 15.1 Live 顶部固定记分条

所有阶段固定：

```text
黄方队名 / 比分 / 剩余时间     当前阶段 · A/B/C     剩余时间 / 比分 / 白方队名
```

BP 时队伍时钟可以显示为 60:00 静止；项目开始后反映权威总时钟。

### 15.2 Live BP 内容

```text
┌────黄方信息────┬────────────────项目池────────────────┬────白方信息────┐
```

观众只看到已经公开的选择。盲选期间两侧只显示“已密封/等待”，揭晓后用短动画展示 X/Y/C。

### 15.3 Live 布阵内容

- A/B/C项目横向排列；
- 双方显示“布阵中/已密封”；

两侧项目画面等权，中央窄栏只放公共项目摘要、状态和系列进程。不能让中央装饰挤压两张主要画面。

项目没有 Live renderer 时，对应侧显示安全降级状态，而不是让整个房间报错。

### 15.5 Live 一方先完成

- 完成方画面冻结并显示“已完成”；
- 该队总时钟冻结；
- 未完成方继续实时展示；
- 不提前显示胜负或具体结果；
- 中央显示“等待双方结束”。

### 15.6 Live 局间与全场结算

局间：

- 当前局结果；
- 系列比分；
- 双方队长确认状态；
- 下一项目；
- 双方时钟暂停。

全场：

- 胜方、总比分；
- A/B/C结果带；
- 出战者；
- 剩余时间；
- 回放入口状态；
- 结算展示结束倒计时不必放在内容主画面。

## 17. 响应式和设备策略

### 17.1 比赛操作端

比赛操作以桌面横屏为正式环境：

- 推荐最小内容宽度 1180px；
- 低于正式宽度时允许只读查看，但关键 BP、布阵和项目操作应提示使用桌面设备；
- 不把完整 BP 项目池压成无法辨认的手机卡片；
- 裁判控制台不提供手机完整操作，仅提供状态和紧急暂停入口可另行评估。

### 17.2 Live

继续沿用现有 1280×720 等比缩放策略。内容内部不随浏览器宽度重新排版，只缩放整个舞台，
避免转播布局在画中画、普通网页和窄屏之间改变信息位置。

## 18. 可访问性与输入

- 所有拖拽都必须有点击或键盘替代；
- 项目卡、席位和布阵槽有清晰焦点态；
- 当前行动方不能只靠颜色；
- 动态倒计时不要每秒通过屏幕阅读器播报，只在 10 秒、5 秒和结束时提示；
- 抽签和揭晓动效遵守 `prefers-reduced-motion`；
- 重要状态使用文本：已密封、已锁定、系统自动选择、等待裁判；
- 黄方和白方在深色、浅色主题下都保持足够文字对比；
- 危险操作确认不依赖红色按钮本身表达后果；
- 错误信息靠近相关控件，并在底部操作条保留全局摘要。

## 19. 动效原则

需要动效的地方：

- 抽签揭晓；
- BP 锁定项目进入槽位；
- BAN 项目从项目池转为禁用；
- X/Y/C揭晓；
- 当前项目从赛程条进入对局；
- 单局结果和全场胜方。

不需要动效的地方：

- 裁判表格和事件日志；
- 在线状态刷新；
- 网络重连；
- 时钟每秒变化；
- 自动选择前的等待；
- 错误、冲突或判罚。

所有关键状态必须先由数据成立，再播放装饰动效；动画失败不能阻止用户进入下一阶段。

## 20. 关键交互验收场景

1. 两名用户同时选择黄2，只有服务端接受者进入席位，另一人得到明确冲突提示。
2. 黄1离席后旧队长立即失去准备、BP和布阵按钮。
3. 双方队长准备后页面进入锁定态，但仍等待裁判或自动放行规则。
4. 先手倒计时到0，所有客户端显示同一个服务器自动选择结果。
5. 盲选期间通过页面、网络响应、Live或日志都不能看到对方选择。
6. 队长布阵提交后刷新，仍显示已密封且不可修改。
7. 一方项目完成后本队时钟停止，另一方继续；结果未提前公开。
8. 裁判改判后双方旧确认失效，并明确要求重新确认。
9. 比赛暂停后项目输入锁定，队长只能确认恢复准备，裁判负责真正恢复。
10. 任意阶段刷新后直接恢复当前状态，不重播阻塞式动画。
11. Live 断线重连获得最新公开快照，不影响选手比赛。
12. 未知项目 Live renderer 只降级单个项目画面，不影响记分条、时钟和聊天。

## 21. 待确认的前端产品决策

1. 双方队长准备后由裁判手动开始，还是可配置自动开始；
2. 队员是否拥有私有的非绑定 BP 建议功能；
3. 队员能否看到本队盲选；
4. 裁判能否看到尚未揭晓的 X/Y；布阵已确定不可见；
5. 已确定：完整布阵仅本队参赛者可见，每场出战者在该场开始时公开；
6. 队长和未出战队员能否看本队实时项目画面；
7. 队长确认是否有倒计时；
8. 选手报告问题后是否按配置自动暂停；
9. Live 从抽签、BP还是 A 局开始出现在大厅；
10. Live 比赛房间是否开放礼物、红包、福袋或预测；
11. 结算画面在 Live 保留多久；
12. 正式比赛对浏览器尺寸、设备和全屏是否做强制检查。

这些决策不会改变“选手比赛站与观众 Live 分离”“裁判控制台独立”“未来项目通过插槽接入”三个
核心视图边界。
