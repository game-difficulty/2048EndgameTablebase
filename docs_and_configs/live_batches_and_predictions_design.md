日期：2026-09-23。已按本方案实现批次协调、房间活动模块及下注；部署和验收记录见文末。
名称、金额档位、净收益上限、超额退款及并列结算已按用户确认更新。
最高分下注的收益上限指净收益，其本金另行退还；65536 独立加注达标后本金不退。结束提示默认 5 秒，结算完成后批间等待 15 秒。

## 65536 独立加注（2026-09-23 增补）

- 先有本批最高分下注，才能给同一选手另下 65536 加注。仅常驻额度，100 / 1000 / 5000 / 10000 Token 档位，可以累计追加。
- 与最高分下注共用 10 分钟窗口、提前封盘及暂停/离线限制。该选手达标或终局后不再允许加注，服务端在下注前核对持久化的结果事实。
- 达到指本局棋盘产生 65536 棋块，不是得分达到 65536；不要求该选手最终最高分，也不限每批首位达标者。
- 达到 65536 时立即发放累计加注额的 8 倍，同盘面同时存在 65536＋32768 时升级为 50 倍，升级只补差额。达标后本金不退；加注 100 两档分别总到账 800 和 5000。失败返还 0，技术性作废退还尚未兑付的加注。最高分无人押中不影响 65536 加注的自身结果。
- 当前及后续批次统一使用 `target-no-principal-v2`：8 倍／50 倍均为总到账，本金不另退。旧批次均已结算，其历史结算数字只读保留，不再保留旧规则执行或展示分支。
- 加注本金与系统奖励独立核算，不进入最高分奖池、不消耗其他用户的下注、不适用按对手本金匹配的最高分赔付上限。前文的奖池守恒仅适用于最高分下注。
- 接口沿用 `/predictions`，请求新增 `kind=target65536`，省略时仍为 `winner`。每笔请求幂等键不能跨类型复用。状态增加 `market.target_bet`（目标、奖励倍数、各选手结果及登录用户个人加注/结算），历史个人结果增加 `target_bet`。
- 使用独立的 target_stakes / target_requests / target_settlements / target_outcomes 表。历史记录原样保留。两项扣款均只操作 paid_balance_units；本批两项结算在同一个 auth 数据库事务提交，并写各自账本事件，重复结算不会重复奖励。
- 内容适配器只产生逐选手 `target_results` 事实，与棋局检查点原子保存；房间活动模块负责事实入账和结算。故障后可幂等重放。福袋仍仅按每批首位 32K/65K 触发，与此独立。
- 下注浮窗分为最高分与独立加注两区，共用截止时间和余额；规则问号浮窗分别说明两套规则。加注区显示绑定选手、累计加注、达标状态、本次成功总到账及独立结算结果。
- 初版验收与旧备份信息保留在部署记录中；2026-09-27 起以本节的 8 倍／50 倍且本金不退为当前规则。

## 2. 批次生命周期

`preparing → running → settling → cooldown → preparing`，另有显式 `void` 终态。
每批具有独立 batch_id、三位 participant_id、三份 run_id、共享 started_at 与规则版本。

- 协调器先准备三份棋盘和三个引擎；全部就绪后提议 batch_start。
- 云端持久化批次与下注市场，返回同一个开始时间及确认。收到确认后协调器释放三路计算。
  “同时”指同一逻辑开始边界，不承诺不同 CPU 进程在同一纳秒执行。
- 每路结束后保存最终棋盘、得分及 ended_at，进入 finished_waiting；禁止自行重开。
- 第三个结束后，云端依据验证过的最终得分生成不可变结果，结算下注。
- 结算或退款完成后等待建议 15 秒，再整批开始。暂停时不启动下一批。
- 异常退出／断网只暂停或恢复该批，不当作死亡，不重新抽种子、不重置下注窗口。
  无法恢复时显式作废本批、全额退还下注后再进入下一批。

本地 `lane_loop` 不再直接 start 新局，由 BatchCoordinator 统一创建。检查点整份原子保存
batch_id、三个 run/generation、阶段；云端恢复裁决优先，不允许旧批次的搜索结果进入新批。
结算不依赖本地 worker 是否在线，也不依赖观众是否在线。

死亡遮罩建议只显示 5 秒，按云端 ended_at 计算，晚加入／刷新页面不重复播放提示。
之后棋盘不再覆盖任何结束文字，仅卡片标题旁保留“已结束，等待本批”状态。
最高分徽标比较本批全部棋盘。自动主屏使用 1000 分防抖：其他存活 AI 领先当前至少 1000 分才切换，
当前 AI 结束则立即切到存活 AI 中最高分者；全部结束后显示最终最高分。手动选择不变。
三局全部结束后主屏可跟随最高分，批次结果和倒计时放在标题区，不长期覆盖棋盘。

所有界面仍适配房间的固定 16:9 外框，批次状态、名单和历史不能改变外框尺寸。

## 3. 房间活动模块与福袋限额

现有 LuckyBags/RedEnvelopes 已挂在 LivePage 且接口已有 room_id，但代码仍位于 live 目录，
福袋触发器仍依赖 content.reached_milestones() 的 (run_id, threshold)。应完成职责拆分：

```
LiveRoom
├─ RoomStage → ContentAdapter（仅提供棋局、批次与事实事件）
└─ RoomActivities
   ├─ LuckyBags（可复用活动引擎）
   ├─ RedEnvelopes（可复用活动引擎）
   └─ Predictions（可复用题目、资金托管和结算）
```

活动模块通过房间能力配置启用；真人直播也可使用红包／福袋，不必伪造 AI run。
AI 房间的策略适配器把 milestone_reached 转换为一次福袋创建请求。通用活动引擎接受
`room_id + trigger_key + reward_spec`，不内置 2048 棋块列表或 run_id 语义。

本房间触发键为 `(room_id, batch_id, threshold)`，threshold 为 32768 或 65536。
三路中第一次跨过对应里程碑即创建，后续全部忽略，因此每批最多两个。
32K 与 65K 可以由不同选手触发，额度与参与规则可先沿用现有配置。

“第一个”以云端接收并验证的房间事件顺序为准，保存首次 run_id/participant_id/content_seq。
不能在事后轮询三个节点集合并按 UUID 排序，否则可能把首达归属写错。
首次跨线时，把检查点、首次事件与 outbox 一起持久化；活动账本按 trigger_key 唯一约束
幂等消费。跨 live/auth 两个数据库不假装是同一个事务，使用持久化 outbox 与重试。
重连、历史恢复和重复消息都不能多发；活动参与和奖励账本仍独立于内容显示。

## 5. 接单与资金

- 仅登录账户可下注；每人每批只选一个选手，可在窗口内追加同一选手，不能换边或撤回。
  同一账户多笔追加合并为一份下注，不按笔数增加“人数”。
- 正常窗口为云端 started_at 起 600 秒；时间由服务器判断，网页倒计时仅展示。
- 暂停／失联期间立即停止接单；恢复后仍使用原始截止时间，不延长十分钟。
- 若十分钟内全部结束或冠军已经确定，先封盘再发布结果。只剩一位存活且其分数严格
  超过其他两位最终分数时，冠军已确定，不能继续接受“已知结果”的下注。
- 拿到结束信息的浏览器不是裁决方。资金事务检查市场状态与服务端截止时间；确定结果的
  服务端状态变更必须先完成封盘，再对观众广播，避免结果已知而市场仍开放。
- 扣款只操作常驻额度 paid_balance_units。不能调用当前优先消耗 bonus 的一般消费入口。
- 使用 TOKEN_UNIT 整数单位，不使用浮点金额。扣款、下注记录、托管记录和请求幂等键
  在 auth 数据库同一事务提交。余额不足整体失败，网络重试返回原结果。
- 金额不采用礼物动态价格倍率；返还与奖励只回到常驻额度，并写带 market/batch/user 的流水。

建议数据：room_batches/room_batch_members；room_prediction_markets（题目、选项、截止、
规则版本、状态、结果）；prediction_stakes（累计下注）；prediction_requests（每笔幂等）；
prediction_settlements（本金、利润、退款、唯一结算键）。资金有关状态同库存储。
下注、封盘和批次终结走同一个房间串行事件处理入口；财务重试由持久化状态驱动。

## 6. 确定的收益规则

“赢取”指净收益，不包括自己的本金。最高最终得分的选手全部进入获胜选项集合。
同一账户的追加先合并；封盘后只按三个选项的总下注额建立固定的两两对手盘。账户数量和
追加笔数不参与匹配，每一份本金最多进入一个对手盘，未匹配本金保留待退。

三个选项记为 A、B、C，总下注为 S_A、S_B、S_C。系统求取 A-B、A-C、B-C 三组匹配额，
使每个选项参与的全部匹配不超过其总下注，并使总匹配额最大。只有两个选项有下注时，
两者匹配额就是较小的总下注；三个选项都有下注时，计算等价于三点最大 b-matching：

- 若最大选项不少于其余两个选项之和，两个较小选项分别与最大选项全部匹配。
- 否则形成三组对手盘；当最小记账单位的总数为奇数时，仅有一个最小单位无法匹配并退款。
- 选项内部按个人下注占比把本金分配到该选项参与的对手盘，使用稳定的最大余数法处理整数取整。

结算时逐组判断：一组对手盘恰有一方押中，才从未押中方等额转给押中方；双方都押中
（例如二者并列第一）或双方都未押中，则该组不发生输赢并原额退回。由此每个用户的最大
损失不超过本人下注本金，同一本金不会同时承担两个对手的赔付。

例如 A 总下注 100、B 总下注 10000、C 无人下注，A-B 只匹配 100。A 获胜时 A 方净赢
100、连本金共到账 200，B 方退回 9900；B 获胜时正好反向。把 B 的 10000 拆成更多账户
或多次追加，不改变 100 的选项匹配额。

公平性来自每一组固定对手盘的镜像关系。对任意 A-B 对手盘，A 方的期望净收益只与
`P(A 押中、B 未押中) - P(B 押中、A 未押中)` 成正比，该差值恒等于 `P(A 押中)-P(B 押中)`。
因此只要各选项命中率相等，每一组对手盘的期望都是 0，每位玩家的总期望净收益也是 0；
这个结论包含唯一赢家、两方并列和三方并列，不依赖其他人如何下注或拆分账户。

计算使用整数最小单位。每组对手盘的双方分配额相等，稳定排序保证重试结果一致。完整核算为：
押中者本金及净收益 + 未押中者退款 = 所有下注，总净收益等于总实际损失；平台不补贴也不抽成。

## 7. 并列与退款边界

例如 Lume 和 Clari 并列最高时，两者之间已固定的对手盘不发生赔付；两者各自与 Vero
之间的对手盘若有匹配，才由 Vero 向对应的一方赔付。Vero 的总损失不会超过其下注本金，
Lume 或 Clari 也不会拿同一份 Vero 本金重复获利。

- 并列最高：全部并列选项获胜；并列选项之间的对手盘退款，只结算它们与落败选项的固定对手盘。
- 三位全部并列、或没有人下注落败选项：无可分配奖金，所有下注者取回本金，净收益为零。
- 无人押中（包括无人押中任何并列最高选项）：所有下注全额退款。
- 批次技术性作废：所有下注全额退款。无人下注则空结算，不遗留奖池、不补贴奖金。
- 某 AI 已死亡仍可能保有最高最终分；不能仅因为死亡就当下注输掉。
- 可恢复的技术故障不判负；不可恢复且明确终止则退款。不得以客户端掉线直接没收本金。
- 幂等结算键唯一；重复 batch_end、重启、重复点击不得重复发放。
- 批次奖励与下注相互独立：福袋不是下注奖池，不挪用红包资金补足下注。

## 8. 实施顺序与过渡

1. 固定身份和统一批次状态，先验证三路起跑、早死等待、全部结束重开。
2. 房间活动模块、持久化首达事件，验证单批两个福袋的数据库级上限。
3. 按已确认的净收益上限、超额退款与并列规则，实现账户托管与纯结算函数，先用隔离账本验证。
4. 下注弹窗、服务端接单截止、幂等恢复、模拟提前确定胜负及各种退款情况。
5. 当前三局并非同时起跑，建议保留为不开放下注的过渡批，全部结束后进入正式批次。
   已创建福袋／红包继续原流程，迁移不得重复补发或撤销已入账奖励。
6. 初版先做模拟结算验收，再启用常驻额度扣款；房间与内容的 16:9、小窗和增量传输继续复用。

当前及后续批次统一使用 `matched-pairwise-pools-v3`。旧规则批次均已结算，其历史结算数字只读
保留；运行时代码不再包含 v1/v2 结算器。v3 用固定且不重叠的两两对手盘保证不同大小的并列
赢家池中，每位玩家在各选项命中率相等时仍有严格为零的期望净收益。

新增网络消息只包含批次开始／封盘／结果及节流聚合的奖池变化；下注本身走 HTTP 幂等请求，
不向全房广播用户私人余额。倒计时由 started_at/deadline 推算，不逐秒发送。
