# 2048 社区站：完整首版产品与技术方案

日期：2026-10-03。状态：用户已确认论坛使用 PostgreSQL。基础版本 `392261a`，第二、三批 `6414707`；第四批投票/问答/公告/搜索/屏蔽/隐私工单/分支回放已实现并本地验证，尚未部署。当前实现与运行方法见 [forum/README.md](../../forum/README.md)，逐项对照及未完成项见 [验收清单](../../forum/ACCEPTANCE.md)。本文是完整首版目标，不能将规划功能等同于已交付功能。用户后续明确优先通过专用语法创建棋盘，手绘改为可选辅助。

本方案基于本地仓库（HEAD `20b8d51`）的代码、配置和近期部署记录，以及本文末尾的官方产品与技术资料。工作区存在赛事代码等未提交内容，调研未改动这些文件。没有登录生产服务器、查询线上数据库、测量真实容量，也没有验证本地代码与线上部署逐字节一致；历史部署报告中的余量不能作为现在可用资源的依据。

## 1. 建议结论

建立独立的 `forum.2048tables.online`（建议域名，尚未配置），定位为 **围绕 2048 玩家、局面和赛事的持久化社区**。

- 内容结构采用“板块 → 主题帖 → 回复”，保留贴吧式的清晰主题与楼层。
- 导航和订阅借鉴 Discord 的频道分组、未读和通知，帖子本身采用适合长文与复盘的阅读布局。
- 核心特色是可交互对局卡：从 Play 选择对局、导入录像、手工绘制棋盘，在特定步数讨论、标注分支并导出分享图。
- 账号沿用主站，论坛前后端独立构建、独立运行，业务数据库与账号、Play、赛事库分离。
- 第一版按完整产品交付：内容创作、讨论、通知、搜索、管理、移动端、隐私、备份、故障降级一起验收；按里程碑建设不等于只交付简陋 MVP。
- 语音房、大规模私聊、原生视频托管、用户自建无限板块不列为首版默认范围。它们是独立产品负担，不能用来替代论坛主链路的完整性。

“尽可能完善”应体现为每个核心流程都有成功、失败、撤销、恢复和运营处置路径，而不是首页堆积所有功能按钮。

### 必须避免的错误复用

1. `backend/live/routes.py` 中聊天缓冲使用 `deque(maxlen=100)`；它不是完整的持久消息历史，不能直接作为论坛帖子存储。
2. `shared_cookie_domain()` 默认主机集合只有根域、www、live、play；新论坛域使用该认证依赖时需要配置 `AUTH_SHARED_COOKIE_HOSTS`。赛事站自行适配 cookie 的做法不能证明论坛无需配置。
3. `authenticate_session_identity()` 是轻量身份验证路径，但返回值不含完整论坛授权信息。论坛需另外获取最小角色与公开资料，不能为了头像把每次请求扩展为不必要的账务/权益读取。
4. `backend/human_play/routes.py` 中录像下载通过 `service.replay_record()` 做查看权限检查。论坛不能读取 `archive` 路径绕过它，或把隐藏录像复制成永久公开附件。
5. Play 档案 `visible`、`deleted_by_user`、公开排名条件和分析档案 `listed/admitted` 是不同语义。能找到记录不等于能公开、能下载、能声称正式成绩。
6. 主站分析 RPL、Play HPR 和 Verse/RPL1 导出并非同一二进制协议；`rplParser.js` 的定长记录解析器不能直接解析所有录像。
7. `manim_anim/` 提供离线动画制作素材与脚本，不是支持用户上传后安全排队渲染的在线服务。首版不把它暴露成任意脚本执行入口。
8. 赛事的公开投影是合适的边界范例：论坛读取公开结果，不读取房间操作凭据、未公开阵容、出数种子等内部字段。

## 5. 三条核心用户流程

### 发一个有内容的帖子

进入板块 → 选择讨论/提问/作品/投票 → 编辑并插入图片或棋盘 → 自动保存草稿 → 预览手机/桌面阅读 → 提交 → 成功页或明确的待审核状态 → 回复/编辑/管理。

发布请求携带幂等键，重复点击和断网重试只产生一篇帖子。编辑带 `revision`，冲突返回 409 并保留用户版本，不能后写覆盖前写。编辑窗口到期或主题锁定时仍可复制/另存草稿。

### 分享一次高分局

Play 终局/个人历史“发到社区” → 社区显示授权对局摘要 → 用户选择封面步数、片段、说明和公开范围 → 发帖 → 读者逐步回放、引用某一步回复 → 可打开主站复盘或在练习环境尝试。

跨站传递 `source + run_id` 等引用即可；不要把 cookie、长期 token、全量录像放在 URL。需要临时授权时使用用户绑定、短期、一次性授权码，由后端验证。

### 从争议局面形成教程

帖子中引用第 N 步 → 插入局面快照 → 作者画箭头/标格 → 用户试走另一路线 → 保存为“假设分支” → 回复附上分支 → 楼主整理并采纳。

分支必须记录起点与每次生成的小块；未记录出数时只能称“下一手演示”，不能假装重现完整对局。进入练习页始终属于非排位上下文，不得变成正式成绩。

## 6. 2048 原生内容设计

### 6.1 对局卡字段

基本字段：来源、原作者、游戏变体、规则版本、分数、最大块、步数、用时（无时间数据则显示未知）、结束时间、撤销/辅助信息（可核实才显示）、封面步数、录像版本、公开性、分析状态、来源链接。

可信状态至少分为：

- **Play 正式记录**：服务端权威来源，仍需明确是否满足榜单条件。
- **赛事官方记录**：来源为赛事公开且可引用的已确认结果，附 `result_revision`。
- **上传录像，已通过一致性检查**：格式、步序、计分一致不等于真人、无辅助或本人创造。
- **手绘局面 / 假设分支**：用户创作，不能授予成绩认证。
- **来源已撤回 / 记录已修订**：保留讨论占位，移除失效的录像访问和过期成绩结论。

“通过录像验证”“归属此用户”“正式榜单合格”是三个独立维度。手动存档的来源和管理审核不能被自动改成 Play 原生记录。

### 6.2 原生块协议（建议）

```json
{
  "type": "replay",
  "schema_version": 1,
  "source": "play",
  "source_id": "opaque-run-id",
  "artifact_version": "sha256:...",
  "rules": {"variant": "4x4", "engine_version": "..."},
  "cover_step": 12000,
  "clip": {"start": 11980, "end": 12040},
  "annotations": [{"step": 12012, "kind": "arrow", "from": [1, 2], "to": [1, 1]}]
}
```

以上仅示范结构。服务端根据可信来源生成分数与标识，客户端不能用 `verified: true` 自证。内容块引用独立资源表；正文 JSON 不直接内嵌大录像。

新建 `ReplayAdapter` 接口，按明确的 `format + version + rules_version` 解析 HPR、Verse/RPL1、分析 RPL，产出一致的 `ReplayManifest / Frame / Move / Metric`。不能靠扩展名猜协议，也不能把所有变体压缩成固定 4×4 十六进制盘面。未知版本展示下载/说明占位，不静默用标准 2048 错算。

首版交互式支持优先覆盖已有 Play 四种尺寸；赛事特殊棋盘只在对应 renderer 和已完成对局导出协议就绪后开放回放。在此之前提供准确的官方赛果卡和来源跳转，不承诺所有赛事变体录像都能直接播放。

### 6.3 局面编辑器

支持 4×4、3×4、3×3、2×4；数值选择、点格绘制、键盘移动选格、擦除、撤销/重做、清空确认、旋转/镜像、坐标标签。特殊块使用显式 cell 类型；只允许当前规则认识的块。

标注包含箭头、圈选、危险格、文本说明；区分棋盘数据和标注图层。保存机器可读 JSON 和预览图，移动端通过按钮操作，不要求精准拖拽。验证尺寸、合法块值、数量、步数范围和字段大小；手绘局面不要求能从初盘合法到达，但必须标注为手绘。

支持插入为单图、局面序列、问答题。导出 PNG 首版必备；短动画导出可以在完成有界渲染任务后开启。不要允许用户上传任意 HTML/SVG/JavaScript 模板来绘制。

### 6.4 回放体验与性能

- 默认封面静止；点击播放后再下载/解析，信息流不自动播放多个棋盘。
- 前后步、播放/暂停、速度、进度拖动、关键帧列表、从此步讨论、片段循环。
- `#p-ID` 定位回复；步数引用同时绑定 `artifact_version`，录像替换时不得把旧讨论挂到新的一步。
- 长录像在 worker 解析，用分段索引与检查点控制内存和 seek 成本；缓存设上限，离开页面释放 worker/大数组。
- 算法分析结果复用已有摘要；新 AI 分析走原有权限、Token/配额与异步任务，不因浏览帖子自动触发计算。
- 在输入框内方向键编辑文本，不夺取为棋盘操作；复用现有 keyboard ownership 设计思想。

### 6.5 海报与短片

PNG 提供横版对局卡、方形分享图与纵向复盘图，包含棋盘、主题、作者、来源标识、分数和帖子链接/二维码。借鉴 `statisticsPoster.js` 的 Canvas 绘制与字体，但抽离为独立渲染器。

短动画需要独立 worker、限时/限帧/限分辨率、队列进度、取消、幂等结果缓存和失败重试；它不是 FastAPI 请求内同步执行的渲染。示例估算：200 帧 × 720×720 × 4 字节约 396 MiB 原始像素，不能同时驻留所有帧；采用逐帧编码或流式处理。

## 7. 通知、公告与治理

### 通知规则

默认通知回复我的内容、@我、审核结果；订阅主题按用户选择开启。关注作者的新主题可进入关注流，是否推送单独设置。批量回复合并为“某主题新增 N 条回复”，点赞聚合，静音优先于一般订阅。

通知写库后再推送；断线根据游标补拉。删除/隐藏内容后通知只显示安全占位，不保留泄露正文的摘要。默认使用站内通知，邮件摘要/浏览器推送需用户主动订阅，不自动发送营销邮件。

公告有 `draft / scheduled / published / expired / retracted` 生命周期，区分发布时间与显示时间、目标站点、是否允许回复、置顶范围及期限。已有静态公告先建立稳定映射和来源记录，逐步替换横幅；论坛不可用时保留主站缓存摘要。

### 权限

| 注册用户 | 发帖、回复、收藏、举报；新账号有上传和频率限制 |
| 稳定参与用户 | 可适度放宽频率和附件额度，不能获得管理权限 |
| 板块版主 | 在授权板块审核、移帖、锁帖、有限禁言 |
| 全局版主 | 跨板块管理、处理申诉和疑难举报 |
| 运营编辑 | 发布公告、专题、精选；不等于系统管理员 |
| 系统管理员 | 管理角色、站点策略、全站封禁与审计 |

采用显式 capability 与 board scope，不把“赞助者/付费用户”“高分玩家”“赛事裁判”自动变成版主。封禁全站账号由账号系统负责；论坛禁言独立存储，避免论坛违规自动剥夺正常游戏权限。

### 内容状态与处置

主题内容使用 `draft / pending / published / hidden / deleted`；`locked / archived` 是独立讨论状态。待审核/隐藏内容仅作者及相应管理员可见，公共列表、搜索、缩略图、SEO、通知都遵循同一规则。

举报支持垃圾广告、骚扰、隐私泄露、内容不当、成绩/来源争议、其他。工单合并重复举报但保留每位举报人的记录；版主选择保留/隐藏/限制互动/升级/处罚，填写原因。用户看到处置通知并可申诉。管理审计包含执行者、对象、原因、前后状态、期限、请求 ID；普通版主不能删除审计记录。

删除保留楼层占位，公开端不泄露原文；历史修订可按策略只对作者/管理员开放，不能让已删隐私仍通过 diff 浏览。附件生命周期用引用计数与审核保留状态管理，不能“删一帖就删被多帖使用的文件”。

初始反滥用建议：可配置的新账号发帖/链接/上传限额；用户与 IP 双维度令牌桶；重复内容检测；链接白名单/风险分；渐进验证。敏感词只是信号，不能替代举报、人工审核和误判申诉。不给发帖数、点赞数直接兑换现有 Token，防止内容农场影响游戏经济。

## 8. 前端设计

### 视觉方向

延续现有 Clear Sans 数字与中文系统字体、暖白底、深棕文字、金棕强调色。深色使用低饱和深灰/深棕正文面板，赛事卡可局部沿用 Live 深海军蓝舞台。6–8px 常规圆角、细边框、少量阴影。金色用于当前板块/主要按钮；绿色用于可解释的验证状态；红色用于错误/处置。

论坛以阅读为主，正文建议 16px、行高约 1.7，标题 20–24px，元信息不低于 12px，正文行宽约 680–760px。棋盘里的数字大小随尺寸调整，长数字不得截断。高分卡的棋盘有优先级，普通文本帖子采用紧凑行，避免所有帖子都成为巨幅卡片。

### 桌面与移动

- 宽桌面：顶部跨站导航；左侧约 200–224px 板块/个人入口；中间弹性主题流；右侧约 240–280px 公告/赛事/板块信息。三栏只在空间足够时出现。
- 帖子详情：减少右栏干扰，主文/棋盘/回复为连续阅读流。楼层锚点、只看楼主、排序、追踪阅读进度都在局部工具条。
- 平板：先隐藏右侧辅助信息，再收起左侧导航。重要公告、举报和发帖不能因此不可达。
- 手机：单栏，板块抽屉；底部社区首页/板块/发帖/通知/我的。跨站主站/Play/直播/赛事保留在顶部菜单。编辑器独立页面，工具可换行，软键盘出现仍能保存草稿。
- 全站主菜单中加入社区时保留现有 Play 首页链接、底栏排行榜入口及替代旧排行榜卡的 2048 AI 卡。

### 主要页面

1. 首页：小型公告条、讨论/作品筛选、最新主题，附适量赛事入口；不用空泛欢迎大屏挤占首屏。
2. 作品区：棋盘封面 + 标题 + 来源状态 + 作者 + 回复，支持尺寸和成绩区间筛选。
3. 对局帖：先主题与正文，再交互棋盘和关键步骤，最后按步数引用的讨论。
4. 编辑器：标题/板块/标签在上，正文中可插入原生块；“从我的对局选择 / 上传录像 / 绘制局面”三条入口并列明确。
5. 通知中心：未读优先、按类型筛选、批量已读；不是弹窗消息刷屏。
6. 管理台：举报队列、内容上下文、历史处置、用户权限与操作原因，在一条处理链路完成。

需要同时设计：首访引导、无结果、请求失败、草稿冲突、会话过期、发帖待审核、资源被撤回、未知录像格式、没有权限、任务排队/失败。登录前草稿按匿名本地空间保存；账号切换不能把前一个用户私密草稿显示给后一个用户。

富文本建议评估 Tiptap/ProseMirror 的 Vue 自定义节点能力，用开源基础扩展实现；锁定依赖版本与许可后再选型，不依赖付费协作功能才能发帖。正文保存版本化 JSON，服务端统一校验节点与生成可安全展示的 HTML/纯文本。Markdown 粘贴是辅助输入，不让用户书写任意 HTML。参见 [Vue node views 官方文档](https://tiptap.dev/docs/editor/extensions/custom-extensions/node-views/vue)。

## 9. 后端建议架构

```text
浏览器
  └─ forum 域同源反向代理
       ├─ Vue 静态资源
       ├─ 公共主题页 HTML / SEO / 分享元信息
       ├─ FastAPI /api/forum/v1
       │    ├─ 轻量身份适配 + 论坛权限
       │    ├─ 主题/回复/通知/审核/搜索
       │    ├─ 独立 forum 数据库
       │    └─ Outbox 持久事件
       └─ 独立 worker：媒体、投影刷新、索引、通知、可选短片

论坛适配层 → Auth 身份接口或现有同机认证模块
           → Play 公开/授权分享投影
           → Competition 公开结果投影
           → Live 公开目录/房间元信息
媒体层     → 受控媒体网关 + 持久文件区（可迁移对象存储）
```

采用独立模块化服务，不为每个论坛模块建立微服务。建议目录：

```text
forum/
  server.py
  backend/
    auth_adapter.py   permissions.py     config.py
    topics/           posts/             boards/
    notifications/    moderation/        media/
    replays/          integrations/      search/
    jobs/             migrations/
  frontend/src/
    app/              pages/             components/
    editor/           replay/            services/
  tests/
```

公共棋盘、颜色、公开身份组件以有边界的共享包/模块抽离；避免论坛构建依赖整个主站 App、全局 CSS 与游戏 session，也避免一次性重构所有旧页面。抽离必须配回归，独立构建不应拉入大体积 WASM/表库和离线动画脚本。

### 存储决策

**已确认：论坛直接使用独立 PostgreSQL，首批本地开发使用 PostgreSQL 17。** 用户已明确选择，取代初稿的 SQLite 起步建议；论坛不提供 SQLite 回退。现有账号、Play、赛事等数据库保持各自现状，账号适配仅作只读查询。

事务层使用 SQLAlchemy 2 + psycopg 3，Alembic 显式迁移。采用用户级事务锁保护幂等提交和写入限流，主题行锁分配楼层，正文/草稿采用乐观修订；通知和 outbox 事件与内容同事务写入。第二批已实现独立 outbox 消费者、失败重试、订阅通知去重和 SSE 收件箱状态更新，部署时必须运行 worker，不能把落库视为消息已经推送。

PostgreSQL 需保持短事务、合理索引、外键与数据约束、连接池上限和语句/锁超时；媒体外置，合并阅读位置更新，不为每次页面滚动或 SSE 心跳写库。上线前将 API、worker 与持久聊天的混合读写一起纳入压力测试，并落实备份恢复、最小权限和容量监控。

首版可用数据库 jobs/outbox 和单独 worker，不强制引入 Redis/Celery。SSE 通知先以游标读取持久事件实现；横向扩容时再加共享 pub/sub，数据库仍是通知事实来源。

### 认证与跨站

- 同机可复用轻量会话验证函数并明确 Auth DB 访问职责，论坛内容不写入 auth 库。
- 拆机时增加可信内部 session introspection，而不是挂载账号 SQLite 到远端或复制用户密码。
- cookie 使用既有 HTTPS/HttpOnly 机制，补论坛域配置，校验退出、封禁、改密后的失效。不可缓存会话撤销结果到长期仍可写入。
- 同源论坛 API 简化 CORS；所有 POST/PUT/PATCH/DELETE 一致执行 Origin/CSRF 检查。共享父域 cookie 下 sibling origin 也要显式校验，SameSite 不能单独承担 CSRF 防护。现有 Play 的方法列表不包含 PATCH，不应原样复制为新 API 的完整策略。参见 [OWASP CSRF 指南](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。
- SSE 建连、重连与存续期间都要有授权/撤销策略；通知按用户隔离，长连接失效后关闭，不能因曾登录就永久接收。

### 数据模型

| 逻辑表组 | 主要字段/约束 |
|---|---|
| boards / tags / topic_tags | slug 唯一、排序、权限、可用标签 |
| topics | board、author、title、type、status、revision、last_activity、pinned_until |
| posts | topic、author、post_number、reply_to、body_json、body_text、revision、状态 |
| post_revisions | 版本、修改者、时间、受权限控制的旧内容 |
| drafts | user、draft_id、revision、正文、附件引用 |
| media_assets / media_refs | owner、hash、MIME、size、尺寸、storage_key、状态、引用关系 |
| replay_assets / replay_bindings | 来源 ID、原作者、协议/规则/内容版本、授权状态、校验结论 |
| annotations / board_documents | step、block_id、棋盘结构、标注、schema_version |
| reactions / bookmarks / follows | 用户与目标复合唯一约束，写入幂等 |
| subscriptions / read_cursors | user、topic/board、通知等级、last_read_post_number |
| notifications / deliveries | recipient、event_id、聚合键、读状态、通知类型 |
| reports / moderation_actions / appeals | 对象、举报者、状态、处理原因、执行者、申诉 |
| roles / role_grants / sanctions | user、scope、capability、期限、授予与处置记录 |
| polls / options / votes | 截止、投票规则、user+poll 唯一 |
| outbox / jobs / idempotency_keys | 去重键、lease、attempt、retry_at、结果引用 |
| optional chat_messages | channel、sequence、author、body、visibility，启用才建 |

主帖也是 posts 的首条，避免正文存在两套存储；已发布楼层分配单调增长且不复用，被删除只留占位。按 `(topic_id, post_number)`、`(board_id, status, last_activity, id)`、`(recipient_id, read_state, created_at, id)` 建索引。跨数据库 user ID/外部资源 ID 是逻辑引用，不能假装有跨库外键；展示时采用批量用户投影避免 N+1。

### API 轮廓（新增建议，均非已存在接口）

| 方法与路径（前缀 `/api/forum/v1`） | 用途 |
|---|---|
| `GET /boards`、`GET /topics?board=&cursor=` | 板块与分页列表 |
| `POST /topics`、`PATCH /topics/{id}` | 发布、改标题/标签/状态 |
| `GET /topics/{id}/posts?cursor=` | 回复流、楼层锚点附近读取 |
| `POST /topics/{id}/posts`、`PATCH /posts/{id}` | 回复与修订 |
| `DELETE /posts/{id}` | 可审计的软删除 |
| `PUT /drafts/{id}` | 按 revision 保存草稿 |
| `PUT /posts/{id}/reactions/{type}`、`DELETE ...` | 幂等表态 |
| `PUT /topics/{id}/subscription`、`PUT /read-cursor` | 订阅与阅读位置 |
| `POST /media`、`GET /media/{id}/status` | 上传、验证与媒体状态 |
| `POST /replay-imports`、`POST /replay-bindings` | 上传适配或引用 Play/赛事公开资源 |
| `POST /render-jobs`、`GET /jobs/{id}` | 受限海报/短片任务 |
| `GET /search`、`GET /notifications` | 搜索与通知补拉 |

所有列表有上限和稳定游标；写请求明确错误码、可重试性与幂等语义；不向客户端返回磁盘路径。主题提交与 outbox 同事务，发布失败不发送通知。通知/索引/海报失败可重试且不会重复创建帖子。

## 10. 搜索、SEO、媒体与安全

### 搜索

首版搜索要真实支持中文。当前 PostgreSQL 首批实现用参数化 `ILIKE` 搜索公开标题和正文，正确转义通配符并限制查询长度/返回量，验证了中文和短查询，但尚未完成全文索引。后续应采用受版本管理的中文分词/索引方案并验证局面术语；不能把默认全文配置视为中文分词。两字词、数字、英文缩写需要单独验收，尤其是“残局”“复盘”“L3”；必要时短查询走受限标题/标签查询。上线前通过真实数据量的执行计划和延迟验证确定索引方案。

固定验收词例：`残局`、`复盘`、`32K`、`32768`、`L3`、`4442`、`3x4`、中文昵称；另测标题/正文分词、繁简策略和标点规范化。索引可异步更新，但隐藏/权限撤销在数据库查询阶段同步过滤。使用全文参数绑定及受控语法，不把用户搜索串直接当 SQL 或不受限的 MATCH 表达式。

公开主题页提供服务端生成的标题、摘要、canonical、Open Graph 图片及基础正文，让外部分享可预览、搜索引擎可读取。Vue 增强回放和编辑交互；不只给机器人返回空 SPA 壳。私密/待审/管理页 noindex 且鉴权，sitemap 只包含公开有效主题。缓存按权限区分，不能把已登录响应缓存给游客。

### 媒体

图片借鉴已有头像安全解码流程，但建立独立论坛存储：格式白名单、真实解码校验、像素/解压限制、EXIF 去除、缩略图、内容 hash、随机文件名、容量配额。图片和录像有不同上限，客户端提示和服务端强制必须一致。初始值可评估图片单张 8 MiB、单帖 12 张；录像按照协议已有上限与压测确定，不能随意放大所有解码器。

待审核文件放隔离区。下载使用合适 MIME、`nosniff`、必要的 attachment；不要允许用户 HTML/SVG 在带登录 cookie 的论坛源执行。公开媒体也经状态网关控制缓存与撤回；CDN 仅缓存确认公开资源并支持清除。私有原件采用授权短期访问。已被他人下载的文件无法撤回，这一点在公开分享选择处应说清楚。参见 [OWASP 上传指南](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

外部链接首版可只显示链接，先做站内域名的可信结构化卡。若实现任意网页预览，需后台 SSRF 防护、重定向重验、内网地址阻止、超时和大小限制；不让帖子浏览触发无约束的服务器抓取。

### 来源撤回

用户删除/隐藏 Play 对局或源站撤销公开授权后，论坛帖子保留其自写正文和安全占位，对局块不可继续播放；缩略图、导出图、索引和缓存按传播事件失效。源服务不可用时，不对需授权资源“沿用旧授权放行”。

作品资源分为“受来源授权约束的引用”和“用户自己授权公开的独立上传”两种，不隐式把前者转换为后者。删除帖子、删除源档案、注销账号是不同动作，需要在 UI 说明影响并保证服务器的行为一致。

## 11. 部署、容量与运维

建议独立 service、独立域/代理配置、独立 releases 和持久数据目录；名字与路径在实施前按实际服务器规划。论坛宕机时主站只隐藏社区摘要或显示暂不可用，不等待论坛才能进入 Play/直播/赛事。

先读 `docs_and_configs/deployment_retention.md`。实际部署前需验证主站/Play 源码基线与已部署 entry/assets、manifest 一致，使用干净 Git 快照与明确 overlay 清单；本地 dirty 工作区不能直接作为生产构建输入。

论坛 PostgreSQL 使用 `pg_dump`/`pg_restore` 或等价原生备份方案，并将备份恢复到独立数据库核验。现有账号等 SQLite 库仍使用 `tools/backup_sqlite.py` 在线备份，不能将该脚本用于论坛 PostgreSQL。媒体清单/内容 hash 一并备份并演练恢复。保持每应用最新 3 个版本及所有 current/进程/回滚 pin 引用版本；备份按 7 天且每库至少 3 份已验证副本保留。健康检查成功后才进行规定范围的清理，报告回收空间和最终占用。上传、录像、活跃 staging 和其他应用不混入部署清理，不自动新增无人值守删除任务。

### 量级估算示例，不是线上测量

- 每日 100 个新主题，每帖平均 3 张各 300 KiB 优化图：约 88 MiB/日，约 2.6 GiB/30 日，仅图片即如此。
- 10,000 个平均 1 MiB 录像约 9.8 GiB，尚未计缩略图、备份、修订和临时渲染文件。
- 10 万条平均 4 KiB 纯文本约 391 MiB，索引/JSON/修订/附件会继续放大。

因此应把媒体与代码 release 分开，首版就做每用户/全站配额与上传预警；对象存储可按增长引入。不能根据前次部署报告的可用空间批准持续视频上传。

监控：API p50/p95/p99、5xx、DB 锁等待与事务时长、上传失败、待审量与等待时长、outbox/job 重试、搜索延迟、SSE 连接与重连、源服务错误、磁盘/备份新鲜度。日志不记录 cookie/token/全文私密草稿。

性能目标建议（上线前确认）：普通列表/详情 API p95 < 300ms、搜索 p95 < 700ms；媒体渲染不占请求线程；初始页面不包含整局录像。用约定设备与网络验证首屏和棋盘流畅度，不把服务器延迟指标当完整用户体验。

压力验收至少覆盖：10 万回复数据集、热帖并发回复、集中点赞、通知扇出、慢客户端 SSE、媒体 worker 同时运行，并测 3 倍预计峰值。未取得访问量基线前不宣称支持多少在线用户。

## 12. 实施顺序与完成标准

| 里程碑 | 交付物 | 通过条件 |
|---|---|---|
| A. 契约与框架 | 身份/角色、内容模型、来源投影协议、迁移、独立构建、基础样式 | 共享登录及退出通过；论坛无游戏核心依赖；选定数据库 |
| B. 论坛主链路 | 板块/发帖/回复/草稿/互动/权限/媒体/基础管理 | 发布-回复-编辑-举报-隐藏-申诉闭环；权限负例通过 |
| C. 2048 作品 | Play 选局、格式适配、回放、步数回复、局面编辑、PNG | 四种 Play 尺寸；来源区分；撤回失效；输入焦点正确 |
| D. 发现与运营 | 中文搜索、通知、公告后台、赛事/直播卡、个人页、SEO | 中文用例、通知幂等、赛果修订、跨站公告降级通过 |
| E. 完整首版收口 | 投票/问答、移动端、中英、可访问性、备份恢复、压测、灰度 | 发布验收清单全部通过；管理者能够独立运营 |

轻量大厅、短动画导出可以并入 D/E 的可控开关，必须在自己的验收通过后启用。采用功能开关逐步对管理员、受邀用户、全部用户开放；里程碑内部依赖可以穿插，但不以开关隐藏安全/权限缺口后宣布完成。

工作量粗估：完整主链路与作品能力约 8–14 人周，另留 2–4 人周处理集成、兼容、性能和运营验收；合计约 10–18 人周。这是范围规划用的量级判断，不是承诺工期；依据尚未实现的模块和未知流量，实施拆解后需更新。原生视频托管、私信、语音和全赛事变体回放另行估算。

### 首版必须通过的代表性测试

1. 游客浏览公开帖子，登录后回到原楼层；退出/封禁后的写请求和通知连接失效。
2. 换用户 ID、post ID、asset ID 不能读写别人的草稿、附件或管理接口。
3. 两次提交、请求重试、worker 重试不产生重复帖子/通知/渲染任务。
4. 同时编辑出现冲突提示而不丢草稿；删除楼层不改变后续链接。
5. 非作者不能授权公开隐藏 Play 档案；源撤回后卡片、缩略图、搜索与缓存全部遵守状态。
6. 合法上传录像仍标“上传”，手绘/假设分支不能成为正式成绩；未知协议可靠降级。
7. 恶意图片、压缩膨胀、超大录像、脚本链接、XSS、跨域写请求被服务端拒绝。
8. 中文短词与 2048 术语搜索命中，待审/隐藏内容不会出现在摘要、结果数和通知预览。
9. 320px 手机宽度、软键盘、深色、长中文标题、长数字、键盘操作与减少动画均可用。
10. 赛事结果改判产生带 revision 的更新，不重复发帖，也不保留伪装为当前结果的旧卡。
11. 论坛或 worker 重启能恢复任务；源站短时故障不使全站页面阻塞。
12. 从干净目录恢复数据库与媒体备份，抽验内容、资源、权限和版本，证明备份可恢复。

上线前准备社区规则、反馈格式、复盘示范、局面绘制教程、FAQ 和一批真实且获授权的精选帖子；设置每个板块的负责人和举报轮值。不要生成假用户、假回复和假活跃度。先邀请愿意提供真实反馈的玩家参与。

## 14. 方案取舍与待验证事项

| 选择 | 优点 | 代价/建议 |
|---|---|---|
| 自建 Vue/FastAPI 社区（推荐） | 贴合现有技术，原生棋盘/录像/分析体验统一 | 通知、治理、搜索、编辑器都是实质工程，需要上述完整范围 |
| Discourse + 自定义对局扩展 | 现成论坛/审核基础，可用 DiscourseConnect 接入现有身份 | 需独立运维与扩展体系；2048 特殊内容仍需开发并维护跨系统协议 |
| 只开 Discord 社区 | 高频讨论便捷、可借鉴频道设计 | 独立网站品牌、公开阅读和深度棋盘交互仍需另建；不能满足全部目标 |

Discourse 的 SSO 能由现有网站承担登录注册，属于可选的替代方案，不必为试验该方案更换主站账号。[官方 DiscourseConnect 文档](https://meta.discourse.org/t/setup-discourseconnect-official-single-sign-on-for-discourse-sso/13045)。

实施前要测而不是猜：生产进程与数据库位置、CPU/RAM/磁盘余量、流量与峰值写入、当前公开录像规模、各协议实际样本、特殊赛事是否有完整对局导出、跨站 cookie/缓存/代理行为、管理者可投入时间。

产品建议已有默认值：公开可读、登录发帖；公共板块优先；帖子为主、聊天为辅；不默认开放私信/视频托管；中英 UI；先接 Play 四种尺寸与赛事公开赛果。尚未确认的域名、规模和扩展优先级不妨碍先实现核心契约。
