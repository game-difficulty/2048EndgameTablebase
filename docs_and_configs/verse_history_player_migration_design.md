# 2048Verse 历史对局继承：实施方案

状态：首版已在代码中实现并完成本地预览，尚未部署。本站认可经站长核验归属后继承的 Verse 历史成绩，**排名资格与本站正式对局相同**。回放是否存在只影响观看和分析，不影响分数资格。本文保留了部分后续扩展设想，首版实际行为见下节。

## 首版实际行为

- 玩家在本人主页“设置”提交一个 Verse 用户名；站长在主站 Admin 的“2048Verse 历史继承审核”中记录人工归属核验方式，再批准或拒绝。批准后，完整 VHS2 缓存也会先按对局时间倒序增量补抓到 **2026-09-24 00:00（UTC+8，含当天）**，按 Verse 对局 ID 合并去重并核对总局数与最高分；无法闭合时做完整多排序复查。本地无完整缓存则运行原有完整采集器。当前批量采集器持有锁时申请保持待导入，后台约每分钟再试，不启动第二个采集进程。
- 四种模式分批写入同一 `human_runs` 表，全部完成后一起公开。Verse 对局与本站自然结束的合格对局共用排行榜、个人最佳和 Best 10。撤销归属会移除整批记录的公开与排名资格。导入局无本站种子、过程证明和默认回放，界面明确标注 Verse 来源和无回放。
- 本人可给单条记录补 `.vrs` 回放。服务器重建动作，核对模式、分数与终盘；成功后同一记录可播放，并进入现有单局多定式分析。补传的回放是玩家提供的路径证明，不能反推为 Verse 官方原始过程证明。
- 首版只在**首次继承前**增量补抓，不在继承成功后持续同步；玩家自行换绑、回放撤回、缓存日期／最高分的站长预览也未实现。部署时需把已采集的 `data/verse-history` 完整档案预置到服务器或设置 `HUMAN_VERSE_ARCHIVE_ROOT`，本地预览数据不会自动迁移。

## 1. 数据与可信边界

`tools/verse-history` 正在按用户名与四种模式生成 `data/verse-history/<用户名>/<variant>.vhs`。正式迁移只接受 VHS2：保存 Verse 对局 ID、UTC 毫秒时间、分数、终盘，以及采集时间、公开局数、最高分和检索轮次。导入前必须完整解码并核验模式、ID 唯一、`unique=page_declared`、最高分和棋盘合法性；不能只看文件存在或 `bulk-state.json` 状态。VHS1、VHR1 缺稳定对局 ID 和可靠时区，不自动合并。

来源接口的 `totalGames` 是 Verse 当时记录的历史局数；其 Score Logging Threshold 可能令低分局不进入历史。VHS2 不含回放、步数、用时、初始种子和本站过程证据。本站**认可 Verse 已记录的成绩**，但不虚构这些缺失信息，也不把“已继承”写成“经过本站原生种子及过程校验”。对玩家展示同级成绩，内部保留来源以供回放、分析、纠错和未来其他站点接入。

本地电脑档案不会自动出现在服务器。要复用已采集结果，须将校验完整的 VHS2 预置到服务器导入库；也可由站长按用户上传单人档案包。未命中才服务器后台抓取。预置不等于认领，归属核验前不影响任何玩家主页或排行榜。

## 2. 一次继承与站长归属核验

用户在自己主页设置页填写一个 Verse 用户名，看到缓存日期、四模式公开局数和申请状态。申请进入 `pending` 不消耗一次继承资格；缺少完整档案则加入后台采集队列。站长页新增“历史继承审核”：待审列表、本站账号与 Verse 用户名、各模式数量／最高分、缓存时间、来源校验和冲突提示，以及批准、拒绝、纠错与审计。页和 API 复用主站站长页的**服务端**管理员鉴权，不靠前端隐藏按钮。

公开用户名本身不能证明控制权。若 Verse 没有可用的官方授权或公开一次性验证码位置，首版由站长人工核验申请人当场控制已登录的 Verse 账号；不收取 Verse 密码或会话令牌，不以静态截图作为唯一证据。批准时记操作者、时间、核验方式和备注。完整导入成功才算用掉一次机会。网络或校验失败可恢复同一申请；成功后普通用户不能改绑或再继承第二个账号，站长可审计后纠错。

需要一张**小型账号绑定／申请元数据表**，例如 `external_account_claims(id, provider, local_user_id, external_account_key, display_name, status, source_collected_at, approved_by, approved_at, proof_note, created_at, updated_at)`，另存必要任务进度和操作审计。它不存每局对局。对已批准绑定施加“一外站账号只属一个本站账号、一本站账号在同来源只绑一个外站账号”的唯一约束；待审申请不能抢占账号。申请与抓取任务均幂等。

## 3. 统一写入现有对局表

所有继承局写入 `human_runs`，不建外站对局表。至少新增 `source TEXT NOT NULL DEFAULT 'native'`；旧记录均为 `native`，Verse 为 `verse`。以“来源＋已批准绑定 ID＋模式＋Verse 对局 ID”生成确定性的本站 `id`，由现有主键防止重试重复；原始来源 ID可放在 `state.imported.source_game_id`。以后若需直接查找来源 ID，可增一列及唯一索引，仍不需要第二套对局实体。

导入行：`status='sealed'`、`reason='imported'`、`eligibility='eligible'`、`visible=1`、`has_replay=0`、`archive=NULL`。`ended` 使用 Verse 对局 UTC 时间；`state` 保存真实分数和终盘，缺失的 `seq/elapsed` 为空、节点为空。5-bit 终盘指数转为现有棋盘实际数值，供最高块和 Best 10 共用。`seed/browser/writer/request_id` 等目前不可空列使用明确的惰性占位值，不伪造本站种子或防回档证明；未来重构表约束时可改为按来源可空。来源采集时间与导入时间留在元数据中，不能把它们当作对局时间。

**后端按来源强制隔离写入入口。** `create/status/writer/online-check/monitor/append/reentry/seal` 与原生异常封局审核只能操作 `source='native'`；导入局不参与进行中槽位、短期许可、防回档、`engine.initial/advance` 或 `human_chunks`。不能只在前端隐藏按钮。导入器是创建 `source='verse'` 行的唯一通道，只能消费完整校验、归属已批准的档案。

大账号可分批写入 `visible=0` 的待发布行；四模式全部完成才发布，避免半个人的记录上榜。发布与绑定状态变更须可恢复、可审计。同一来源 ID 若与已入库的分数、时间或盘面冲突，暂停并报站长，不静默覆盖。原有全量采集器替换 VHS2 时先删旧文件再重命名；新增的增量刷新器先准备四模式新文件，再对已有文件直接重命名替换，不修改正在运行的全量采集器。

## 4. 排行榜、BEST、主页

现有排名资格 SQL 必须明确容纳已批准的导入局：

```sql
visible=1 AND eligibility='eligible' AND (
  (source='native' AND (reason='game_over' OR 原生异常封局获站长批准))
  OR
  (source='verse' AND reason='imported' AND 账号绑定已批准并发布)
)
```

批准的 Verse 分数参与四模式总榜／周榜、每人最佳、棋盘 BEST、个人主页四模式最佳和 Best 10，使用同一排序与并列名次规则。周榜按 Verse 原局时间归周，不能按导入时间归周。原生重开／中断仍需原有站长审核。若站长撤销归属，应撤销整批记录的可见与上榜资格并审计。

历史记录继续在同表按模式、时间或分数查询；缺失的步数／用时不展示。无回放的继承局回放和本人分析按钮灰置，成绩与排名不受影响。Best 10 可用来源终盘；分享图可在角落标明来源，**不因此降低成绩等级**。本人隐藏的本站局仍对本人主页隐藏。主页、榜单、Best 10 查询只选择摘要字段，不读取 `archive` BLOB。

## 5. 本人补回放

本人可在某条继承局上传 Verse 原始回放。后端限制文件和解压大小、步数及并发，独立解析和重建合法移动／出数，核对模式、终分和 VHS2 终盘。失败不挂到记录；成功后压缩写回**同一 `human_runs.archive`**，置 `has_replay=1`，不新建对局也不改分数资格。`source='verse'` 决定下载文件名与回放解码分支；现有 `/api/human/replays/{id}` 固定按 gzip/HPR 返回，需要按来源改造。前端预览不能代替服务端核验。

补回放后本人可进行现有单局多定式分析；现有入口只接收原生 HPR，须增加 Verse 回放转分析器输入的分支，同时保留相同所有权、报价、单人／全局并发及最多 60 个待处理分析项。没有回放仍不能分析。若补传回放有误，可撤回回放或分析结果；是否撤销来源成绩则是单独的站长裁定，不由普通上传校验自动决定。

## 6. 缓存、增量、资源

先按规范化用户名找四个完整 VHS2。命中后也执行增量刷新：四种模式分别以 `sort=date&desc=true` 从第 1 页抓取，包含 2026-09-24 当天（UTC+8）并读完跨越边界的整页，然后按 Verse 对局 ID 与缓存合并。同一毫秒可能有多局，因此不只靠时间去重。每种模式至少读 1 页；新增局数多于一页时继续分页。前后 `totalGames` 和 `hs` 必须稳定，合并唯一 ID 数量与最高分必须等于 API 声明。否则完整执行日期升／降、分数升／降多排序复查。同一 ID 的时间、分数或盘面发生变化时停止导入且不覆盖证据；旧 ID 仅从 Verse 当前结果消失、其余交集完全一致时保留此前完整采集的记录，在绑定审核日志中记录远端移除数量和 ID 后继续。四模式全部验证成功才替换缓存并进入数据库导入。无缓存或缓存不完整则先按原有方式全量采集，再刷新已存在的旧分段。每次请求保持串行、限速及 429／5xx 退避，不在同步 HTTP 请求或长 SQLite 写事务中抓取。

一次继承成功后**不自动持续同步 Verse 新局**。批量采集器运行期间，已批准申请等待约每分钟重试，防止两个采集器同时写同一份缓存。

运行中目录的一次只读快照约 102 个 VHS2、总计约 2.64 MB；例：3x3 的 3,599 局文件为 50,354 B。这不是最终全集或 SQLite 占用预测。逐行 JSON、索引和 WAL 会显著大于 VHS2；用大账号样本实测磁盘和榜单延迟。对 2 核、约 2 GiB、此站可用带宽可能仅 0.5 Mbps 的服务器，优先离线预置、受限采集、摘要查询和回放单独限流。

## 7. 实施与验收

已实现：`human_runs.source` 与原生写入保护、同级资格 SQL；账号绑定／申请与站长审核；VHS2 校验、分批导入及首次继承前的增量刷新；排行榜、BEST、主页、Best 10；本人补回放和分析。后续仍需考虑继承成功后的持续同步。重点测试四模式混合排名与 PB、周榜按原局时间、同 ID 重试、用户名大小写、抢绑、半成品档案、半途导入、撤销归属、导入局误入原生 API、无回放仍上榜、补回放不改资格，以及增量边界、总数不闭合和分页漂移。
