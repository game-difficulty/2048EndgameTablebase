# 单局残局分析展示图设计

2026-09-25 起实施。展示图对应**一局对局的一个定式/目标组合**。同局选择多个组合时各自生成一份报告；同一组合匹配的多个残局阶段汇总到同一张图。2026-09-26 已确定 4×4 的服务端评级规则；公式仅在后端使用，不在页面披露。

分析器阶段摘要与按需读取接口已实现：切段时记录与报告同源的吻合度和统计，从归档输入取每步用时，汇总后写入 `human_analysis_summaries`。旧版 Verse 归档若已将未知时间转换为 100 ms，标记时间数据有损；新导入以 `0xffffffff` 保存未知间隔。现阶段 `poster_eligible` 仅对能由 4×4 定式元数据确定目标的 16K/32K/65K 开启；其他变体仍可获得分析摘要，暂不开放出图。本人历史记录的分析弹窗已接入展示图预览、同局多个定式切换与浏览器端 PNG 下载。有合格时间数据的 4×4 图显示正式等级；时间不足或有损时显示“待评级”。

## 用户看到的内容

`frontend/src/human/analysisPoster.js` 是 2360×1640 Canvas 绘制器；`docs_and_configs/mockups/analysis-poster-preview.html` 仍可用示例数据切换四种棋盘、中文/英文及 SSS—F 等级外观。`frontend/public/human/play-qr-art.webp` 与 `play-qr-backdrop.webp` 成对组成指向本站入口的艺术二维码。正式分析弹窗只对后端 `poster_eligible` 的本人摘要开放出图，切换定式时按需读取对应小摘要；样稿中的 `SSS` 只是视觉占位，正式等级由后端给出。

颜色以深紫黑 `#18171f` 为底，沿真实最终盘面的色块生成重度虚化背景；数据面板为近黑半透明，文字以暖白和浅紫区分层级，PB 增量用淡金色。棋块保留经典色作为画面唯一高饱和主体，用户自定义主题可通过 `tilePalette` 传入。布局的左右大块在 4×4、3×4、2×4、3×3 均保持同一位置与高度，只有左侧棋盘行列与棋块尺寸变化。上方头像可传同源图片，缺失时显示首字母；底部二维码是真实可扫描的本站网址。

参考音游结算图的横向层次，采用 2360×1640 的画布比例。右上角是玩家昵称与头像；主视觉左侧是**终局盘面**，不误用阶段终点棋盘；右侧依次是本局得分与等级位、Max Combo、平均吻合度、评价计数。只有该局在当时严格刷新个人最佳时显示 `NEW BEST`、前 PB 和增量。底部写本站网址、引导别人进入本站对局及制作展示图的文案、**指向本站入口而非回放或图片的二维码**，以及**对局结束日期**；日期按北京时间格式化，图面不显示时区后缀，不能使用分析或下载日期。

视觉样稿的左侧棋盘容器为直角布局的矩形。艺术二维码使用 `tools/assets/play-qr-art-source.png` 的原创 2048 插画；从中制作的 `play-qr-art-cutout.png` **带真实透明背景**，保留棋块与山石的不规则轮廓，没有铺底色或圆形渐变。`tools/generate_play_art_qr.py` 将 H 级纠错矩阵做成另一透明编码层，浅色码元半透明，定位、定时及校正图形保持高对比度；仅四格必要静区使用逐级变淡的浅色码元，以满足缩图识别。插画向左微移，使二维码中心的小号 2048 金色棋块位于背景黄色菱形中央。两张静态 WebP 在浏览器叠合，出图无需请求第三方二维码服务。完整海报在原尺寸、75% 与 50% 缩图、JPEG 质量 80 下均由 ZXing 读取；OpenCV 在原尺寸与 JPEG 质量 80 可读，在两种缩图上未读取，因此实际分享仍宜保留原始 PNG。棋块数字按对局站共用 `getTileLabelStyle()` 的默认字号档位绘制，使用 Canvas 实际字形边界居中。得分采用较小字级，等级占右侧独立区域；SSS、SS、S、A 至 F 使用各自的色阶与柔和光效。等级只演示外观，不由前端计算。

海报中的二维码不加外框或纯色留白框；插画自身透明，靠原有不规则图形与页脚衔接，不再使用圆形光场。编码层的静区仍要保持足够对比；其上缘低于评价统计栏底部，保持可见间隔。尺寸以分享图里能扫码为下限，不让它覆盖统计文字。图像化外围的兼容性依赖识别器，出图后必须用最终尺寸而非仅用独立原图验证；两张资源必须一同加载。

二维码底图使用内建 imagegen 生成，提示词为："Use case: stylized-concept. Asset type: original square illustration to be woven into a functional artistic QR code for a 2048 puzzle game's result poster. Make a polished, immediately recognizable 2048-inspired scene: an elegant central stack or constellation of square numbered-tile shapes, with one luminous amber-gold tile as the visual focus, surrounded by deep plum, violet and muted rose geometric fragments. Flat-to-painterly editorial illustration with fine texture, sophisticated rhythm-game album-art mood. Bold composition readable when reduced to a small square. Keep the corners and outer 15% relatively light and visually quiet so functional QR finder patterns can be overlaid later. No QR code, no pseudo QR patterns, no text, no numerals, no logos, no watermarks, no people or existing characters. Square canvas." 正式码由本地脚本预生成，底图生成不参与玩家出图流程。

页面以小字标出棋盘模式与完整定式名（如 `free10-512`）。不另列“16K/32K/65K 目标”；底部展示“残局数”和“残局总步数”。样稿中的 SSS—F 仅供检查样式，正式数据使用后端等级。

背景由最终棋盘的色块/排布放大、重绘并重度模糊，叠加暗色蒙层，形成参考图那种有颜色与轮廓的虚化背景；不要将参考图中的歌曲封面或人物直接用作资产。可额外允许用户选择局内某一帧作为装饰，但须标出步号，且左侧主棋盘仍默认显示最终盘面。不同变体仅改变棋盘的行列形状，其余栅格和信息层级保持一致。头像加载失败时以昵称首字母块回退。

## 定式、目标与阶段边界

第一阶段只对 16K、32K、65K 残局对应的定式/目标组合开放出图。映射必须由后端表库目录与定式元数据给出，前端不可根据 `free10-512` 之类的字符串猜；图面只显示定式名。这里的目标数字是要从自由区域拼出的棋块，不一定等于最终合成的大棋块。例如 4×4 的 9 格 65K 残局有七个已占的大块，需拼出另一个 **512**；`free10-512` 是 32K 残局。不同棋盘与遮罩先验证适用性，不照搬 4×4 的格数公式。

一个阶段沿用**现有分析器的切段定义**：同一 `(定式,目标)` 匹配的局面开始，到大块布局变化或回放结束而切段。即使玩家最终死亡、没有合成目标，这个残局阶段仍然成立。`Analyzer.generate_reports()` 在切段时按现有门槛生成该阶段的分析 TXT / RPL，文件名包含该阶段 `goodness_of_fit`，随后 `clear_analysis()` 清零；同一局可因此生成多个文件。生成展示图所用的吻合度就是**各文件对应阶段的整体吻合度**，而非逐步比率重新求平均。结构化摘要应在写文件时记录相同的未舍入值、文件名中的四位小数显示值、阶段起止步号、阶段实际总步数及切段原因。

纳入主图统计的阶段需要满足：有该组合的分析产物、实际总步数 `>= 20`、该阶段整体吻合度 `> 0`。恰好为 0 的阶段与不足 20 步的阶段排除；若未舍入值大于 0 但四位小数显示为 `0.0000`，对外应显示 `<0.0001`，不能误写为 0。为避免现有 TXT 的 `len(text_list)>100` 门槛与新规则冲突，应在切段钩子里独立产生摘要，明确 RPL/TXT 的对应关系；不能仅靠目录扫描或文件名反推步数。

同一局可有多个纳入统计的阶段。对于所选的同一组合，阶段步号区间不应重叠；若代码演进后出现重叠，先按原始动作序号去重，再计算时间与评价次数。跨阶段的连击不拼接；每段的连击遵循分析器对强制步的统一定义。

## 指标口径

| 指标 | 单阶段来源 | 跨阶段与全局汇总 |
| --- | --- | --- |
| 得分、最终盘面、对局日期 | 已归档对局的权威摘要 | 用**全局单局**数值，不随阶段相加 |
| 评价次数 | 分析器逐步判定的稳定代码；另计强制/未评价步 | 同一组合各纳入阶段相加；强制步不进入 Perfect 率分母 |
| Max Combo | 每段连续最优决策最大值 | 各纳入阶段取最大值，不相加、不跨段衔接 |
| 平均吻合度 | 与该阶段 TXT/RPL 文件名对应的**整个残局吻合度** | 排除 0 与不足 20 步阶段后，对各阶段吻合度取**算术平均**；每段等权，不按步数加权 |
| Perfect 率 | Perfect 数 / 有效评价步数 | 总 Perfect 数 / 总有效评价步数，不能平均阶段百分比 |
| 阶段步数与用时 | 原始回放的起止动作序号与各步毫秒间隔 | 分别统计各段 `total_moves`、`timed_moves`、`valid_timing_ms`、`mean_ms_per_timed_move`；跨段需要时以有效计时步数合并 |

现有 `Analyzer.goodness_of_fit` 在**一个阶段内部**通过逐步比率连乘得到，代表这个完整残局的吻合度。展示图要对**多个残局的最终吻合度作算术平均**：`mean_fit = sum(stage.goodness_of_fit) / included_stage_count`。阶段长短不改变其权重。这与把所有单步比率平均、或将阶段吻合度按步数加权，是不同指标；后一种口径不用于本图。

每个阶段按回放动作序号提取每一步的 `delta_ms`，记录总步数，并仅将**非空且 `0 <= delta_ms <= 1,200,000`** 的步计入有效总用时和有效计时步数。`mean_ms_per_timed_move = valid_timing_ms / timed_moves`；单步超过 20 分钟、空值或超时标记（Verse 旧格式约 4194304 ms 的量级）均排除。分母必须是有效计时步数，不能用全部步数稀释。`timed_moves=0` 时平均值为 `null`，不可当作 0 秒参与评级。多阶段的整体平均步时用 `sum(valid_timing_ms) / sum(timed_moves)`，同时保留各阶段的值。**这一口径下的单步平均用时参与 4×4 正式评级**。

当前 HPR2 归档逐步保存 32 位毫秒间隔，转换为 RPL1 时也写入间隔；但 `ReplayDecoder.record_list` 目前只保留棋盘、分数、动作和出数，**没有保留时间**。生成结构化摘要时要从对应原始归档另行按序号解码时间，或扩展解码器保留时间，并确认分析记录与回放动作一一对齐。还要修正 Verse 旧格式导入：现在 `_legacy()` 把未知间隔替换成 100 ms，已归一化的旧档案无法再区分未知与真实 100 ms。新导入必须保留未知标记；已导入旧档若无原文件可重建，应标识为时间数据有损，不可把替代值算入官方速度评级。

## 评级系统（4×4）

等级序列为 SSS、SS、S、A、B、C、D、E、F。原始指标至少保存各阶段整体吻合度及其算术平均、全局得分、各阶段总步数和有效计时步数/用时、跨阶段平均单步用时、Max Combo、Perfect 率、纳入阶段数、定式和目标。后端依 4×4 定式元数据判断该组合属于 16K、32K 或 65K 残局，并据此计算等级。Max Combo 和 Perfect 率继续展示，但不参与本版评级。计时有效步为 0 或来源时间有损的结果不参与正式等级。

评级规则保留在后端，不进入网页文字与分享图。新分析摘要保存 `grade_version` 和字母等级；旧摘要可凭已有的小型结构化数据即时补算，无须重新分析或读取回放。等级不可由浏览器自行决定。分析器升级后旧图保留其版本信息，必要时明确标注“旧版评价”。

## 后端输出与持久化

沿用现有“归档对局 ID → 服务器读取归档 → 多定式分析任务”链路和并发/额度限制。在 `Analyzer.generate_reports()` 的**同一次付费运行**中于每次切段及最终写文件处新增结构化结果钩子，逐段输出同一 `goodness_of_fit` 未舍入值、起止步号、总步数、评价计数和连击；另将原始归档中的各步时间按步号合并。无需第二次表库查询，也不通过解析 TXT 文件名或过期 ZIP 生成官方摘要。任务项完成时，小 JSON 摘要单独写入持久表；现有 TXT/RPL/ZIP 继续供详细下载，按现有过期策略清理。

建议唯一键为 `(run_id, pattern, target, analyzer_version, metric_version)`；字段含每段 `start_seq,end_seq,total_moves,goodness_of_fit,stats,max_combo,timed_moves,valid_timing_ms,excluded_timing_moves,mean_ms_per_timed_move` 与聚合结果、任务 ID、创建时间、运行状态。最终棋盘、分数、结束时间与来源从对局归档摘要关联读取。摘要通常是 KB 级，不复制回放 BLOB。数据库写入在单项分析完成后短事务进行，失败时不把任务标记为拥有可分享结果。

接口建议：

1. 原有任务状态每个完成项增加 `summary_id`、`poster_eligible` 和不能出图的明确原因；不返回大回放。
2. `GET /api/human/runs/{run_id}/analysis/summaries`：本人查看本局已完成的各组合摘要列表；仍核对归属、封存、`visible=1`、回放及资格。**隐藏于主页的本人对局仍不可见**。
3. `GET /api/human/analysis/summaries/{id}`：本人读取单个组合的阶段和聚合指标、PB 快照、头像同源地址及出图所需元数据。
4. 暂不需要公开报告分享接口。图片可在浏览器下载并自行分享；二维码统一指向本站入口，分享图片无需服务器托管。

PB 判断以**此局结束时**同变体之前已认可且展示的最高成绩为准，分数必须严格大于前 PB；比较使用结束时间与稳定的对局 ID 排序。历史 Verse 数据若后来补录，旧快照可能改变，所以首次生成摘要时固定所依据的前 PB、增量与口径版本；资料重算需显式更新版本，不能悄然改旧图。第一局的前 PB 可为 0，是否显示 `NEW BEST` 属展示规则，先固定在服务端。

二维码固定指向本站的稳定入口地址，并配“来本站对局、分析并生成展示图”一类引导文案。它不指向个人回放、分析报告或生成的 PNG，故无须为了二维码增加公开分享接口或持久图片存储。

## 前端交互与渲染

本人在历史记录点“回放分析”，为该局选择至多六个组合并确认额度；任务完成后，每个可出图的组合出现“生成展示图”。点击后是海报预览弹窗：默认包含该组合所有满足 `>=20` 步且吻合度 `>0` 的阶段；同局多个组合的海报可在预览中左右切换，各自独立计算。可下载 PNG，不要求服务器存图或公开分析摘要。若该组合没有合格阶段或不属于 16K/32K/65K 残局，则说明原因，不生成带误导性等级的图。

前端复用 Best 10 海报的 Canvas 棋盘/字体/PNG 导出基础，新增横向布局和本地二维码生成。浏览器仅拉取小摘要、同源头像及必要的公开资料，**不为了出图拉整份回放、ZIP，亦不请求服务器逐次栅格化**；这契合约 0.5 Mbps 可用带宽。背景优先用离屏棋盘渲染再模糊，浏览器不支持 Canvas `filter` 时退化为预绘制柔和色块。头像应经本站同源服务或具备正确 CORS 的资源加载，否则 Canvas 导出会被污染。预览与导出用同一绘制函数，保证两者一致。

## 验收点

- 同局同组合出现多个合格阶段时，评价次数相加、Max Combo 取最大、阶段整体吻合度**等权算术平均**；换一个组合绝不混入前者。
- 达成目标后切段和死亡/离开定式后切段都可纳入；仅排除吻合度为 0 或总步数不足 20 的阶段，不能把未达成目标误认为无效。
- 每阶段保留总步数、有效计时步数、排除计时步数、有效用时及平均单步用时；空值与 `>20` 分钟排除，旧 Verse 未知时间替代值不得混入评级。
- 最终棋盘对应整局终态；PB 是截至对局日期的前 PB；二维码始终指向本站入口。
- 分析结果 ZIP 过期后，结构化摘要仍能读取；撤销展示资格后本人也不可从主页进入该摘要。
- 所有图像像素在浏览器生成，预览和下载同版；头像失败/跨域、Canvas 模糊不支持、四种棋盘尺寸均可回退。
