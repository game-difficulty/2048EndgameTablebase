# Play 完整排行榜设计

## 页面与范围

完整排行榜从对局页浮窗迁移为独立地址 `/leaderboard`。对局页右侧栏仍只读取当前分数榜前 10 名和本人名次；“完整榜单”跳转到独立页面，不再下载前 100 名。

页面状态全部进入查询参数，刷新、前进后退和复制链接都能恢复筛选：

`/leaderboard?type=score&variant=4x4&period=all&page=1`

榜类型如下：

| 榜类型 | 变体 | 周期 | 每位玩家的参榜记录 |
| --- | --- | --- | --- |
| 分数榜 | 4×4、3×4、3×3、2×4 | 总榜、近 168 小时 | 该范围内最高分对局 |
| Rating 榜 | 四种变体 | 仅总榜 | 当前 B10 Rating |
| 综率榜 | 仅 4×4 | 仅总榜 | 当前累计 32K 综率 |
| 数量榜 | 四种变体 | 仅总榜 | 4×4 的 32K、3×4 的 4096、3×3 的 1024、2×4 的 512 达成次数 |
| 残局实力榜 | 首版仅 4×4 | 总榜、近 168 小时 | 所选完整定式下该玩家最好的正式分析结果 |

所有榜都只纳入 `RANKABLE_SQL` 定义的公开、有效成绩。隐藏局对本人也不进入榜单；站长批准的非自然结束局和完成归属核验的 Verse 对局与本站自然结束局地位一致。每页固定 50 人，默认第一页。

“近 168 小时”统一按对局结束时间 `ended_at`，不按分析完成时间。这样分析一局旧对局不会让它重新进入近期残局实力榜，重复分析也不能刷新近期资格。

## 页面展示

页面顶部先放榜类型标签，再放该榜允许的筛选项。不可用的筛选直接不出现，而不是显示禁用控件：

- 分数榜：变体、总榜／近 7 天。
- Rating 榜：变体。
- 综率榜：固定 4×4。
- 数量榜：变体；指标名称随变体显示为“32K 数量”“4096 数量”“1024 数量”或“512 数量”。
- 残局实力榜：首版固定 4×4、完整定式、总榜／近 7 天。完整定式使用 `(pattern,target)` 作为稳定键，界面显示 `free10-256` 这类名称；可按 16K／32K／65K 分组，但组名不参与排名。

桌面端采用统一表格骨架：排名、玩家、该榜主指标、辅助信息、对局。用户名进入个人主页；存在公开回放的对局分数或“查看对局”进入回放。移动端将同一行折成卡片，不横向滚动。

- 分数榜主指标是分数，辅助信息为对局日期。
- Rating 榜主指标是 B10 Rating，辅助信息显示纳入计算的对局数；不足十局时明确显示“基于 N 局”。
- 综率榜主指标是百分比，辅助信息显示“通过阶段 / 总阶段”和达到 32K 的正式对局数。首版要求玩家至少有 10 局最大棋块达到 32K（`rate_32k_candidate_games >= 10`）才进入榜单；进入榜单后仍直接展示分母和对局数，避免掩盖样本量。综率由终盘六层事实计算，无需回放覆盖。
- 数量榜主指标是达成次数，辅助信息显示该玩家正式记录总数。
- 残局实力榜以与分析海报一致的 SSS—F 徽章作为主指标。内部加权分只用于排序，不进入 API，不写入页面。辅助信息展示平均吻合度、有效残局数、评价步数、该局分数和对局日期。相同字母等级仍按内部精确结果排序，页面用简短说明告知这一点，不披露公式或加权分。

残局实力榜每个 `(玩家,变体,定式,目标,周期)` 只占一个席位，选该范围内内部加权分最高的分析结果，避免同一玩家用多局占满榜单。并列时依次比较平均吻合度、最终局分数、平均步间隔（更短优先）、对局结束时间和结果 ID，保证排序稳定。

分页区显示总人数、当前第几页及首／前／后／末页。切换榜型、变体、周期或定式时回到第一页。页面不轮询，只在首次进入、切换筛选、翻页或用户主动刷新时请求。

## 数据来源与新增结构

现有数据可直接复用：

- `human_player_ratings` 已持久化每位玩家每个变体的 PB 和 B10 Rating，并已有 Rating 排序索引。
- `human_player_statistics` 已持久化四种变体的成就次数与 4×4 综率分子、分母和覆盖数。
- `rolling_player_best` 已维护近 168 小时每位玩家的最高分；游戏页 Top 10 的 `rolling_board_entries` 继续只保留小快照。
- `human_analysis_summaries` 已保存每局、每个 `(pattern,target)` 的持久化小摘要，但 JSON 不适合作为排行榜排序源。

需要补充以下窄字段和表：

### 总榜派生字段

给 `human_player_ratings` 增加 `pb_run_id`，总分榜可用 `(variant,pb_score DESC,...)` 索引分页，再按 50 个 ID 连接对局摘要，不再扫描或排序 `human_runs.state`。

给 `human_player_statistics` 增加：

- `primary_achievement_count`：该变体数量榜所需的计数；
- `rate_32k_value`：`passed / total` 的持久化数值，无分母时为空；
- 对应 `(variant,primary_achievement_count DESC,...)` 和 4×4 综率排序索引。

这些值与现有 `features_json`、综率分子分母在同一次刷新或重建中写入。Verse 批量／增量导入、归属撤销、人工审核和回放补齐原本就调用 `rating.refresh_player` 或 `statistics.rebuild_player`，扩展这些路径即可，不增加回放读取。

### 残局实力事实表

不建议再创建一个物理 SQLite 文件。分析摘要、对局资格和榜单更新需要一致提交，拆库会引入跨库恢复问题。应在 `human-play.sqlite3` 中新增独立的结构化表；它在逻辑上就是单独的排行榜数据库层：

`human_analysis_results`

- `summary_id` 唯一，另存 `run_id`、`user_id`、`variant`、`pattern`、`target`；
- `run_ended_at`、`result_created_at`；
- `metric_version`、`grade_version`；
- 私有 `weighted_score`、公开 `grade`；
- `mean_goodness_of_fit`、`mean_ms_per_timed_move`、`max_combo`、`stage_count`、`evaluated_moves`、`final_score`；
- `eligible` 与更新时间。

`human_analysis_best_all` 和 `human_analysis_best_week` 分别保存每位玩家、每个完整定式的当前最佳 `result_id`、内部值及稳定排序字段，并建立：

`(variant,pattern,target,weighted_score DESC,mean_goodness_of_fit DESC,final_score DESC,...)`

索引。读取榜单只扫描这一窄索引。

现有评级函数应拆成两个内部函数：一个返回精确加权分和字母等级，另一个只返回供前端摘要使用的字母等级。精确加权分仅写入 `human_analysis_results`，不放入 `summary_json`，也不由任何公开接口返回。

分析任务只有在成功生成结构化摘要、能够给出正式等级且对应对局仍满足 `RANKABLE_SQL` 时才写入实力事实表。失败、取消、待评级、少于 20 步或吻合度为 0 而被排除的结果不参榜。对同一局和同一定式重新分析时按现有唯一键更新同一事实，再重算该玩家在该定式的最佳项。

如果评级版本变化，从结构化摘要中的吻合度、速度和局分批量重建实力事实与最佳表；不重新读取回放，不重新查表，也不扣 Token。旧、新版本不可混排，版本切换采用完整重建后一次切换。

## 近 168 小时维护

分数周榜继续复用 `rolling_player_best`。完整周榜不读取只含 Top 100 的 `rolling_board_entries`，而是直接按已建立的 `rolling_best_score` 索引分页，因此可以展示第 101 名以后而不扩大游戏页快照。

残局实力周榜采用与滚动分数榜相同的事件维护方式：

1. 新分析结果完成时，如果对局结束时间仍在窗口内，比较并更新该玩家、该定式的周最佳。
2. 每个定式保存 `next_expiry_at`；后台维护器定期剔除过期最佳，并只为受影响玩家从窄的 `human_analysis_results` 中寻找窗口内次佳。
3. 页面请求只检查版本和过期状态；正常情况下直接读最佳表。服务中断后的大量补偿由后台分批完成，避免第一个访客承担完整重建。
4. 总榜同样在新结果、资格撤销和评级版本迁移时增量维护，不在 GET 时聚合 JSON。

## API

保留现有 `GET /api/human/leaderboards?limit=10` 供游戏页分数榜使用。新增完整榜单接口：

`GET /api/human/leaderboards/full?type=score&variant=4x4&period=all&page=1&page_size=50`

残局实力榜额外接受 `pattern` 和 `target`。服务端按榜类型验证合法组合，固定 `page_size=50`，不允许客户端借此一次拉取大量数据。响应包含：

- 规范化后的筛选值；
- `entries`；
- `page`、`page_size`、`total`、`page_count`；
- `version`、`updated_at`，滚动榜另含窗口起止时间；
- 可用定式目录可由一个小型 catalog 响应提供，只列当前正式评级支持的组合。

接口永不选择 `archive`、`state` 或分析报告文件。对局字段通过 `pb_run_id`／`result.run_id` 读取现有摘要列；用户名对本页 50 个用户一次批量解析。公开响应不含“本人名次”，因而可以使用 `ETag` 和短期公共缓存；筛选状态不自动刷新。典型 50 行响应预计 gzip 后约 3–8 KiB。

直接页码采用 `LIMIT 50 OFFSET ...`。数据源都是每用户一行的窄表和覆盖排序索引，几万玩家范围内成本很低；无需在每次请求执行历史对局排序或分析 JSON 计算。排名号由排序位置生成；主指标完全相同的分数榜可沿用并列名次，其余榜使用完整稳定排序后的席位序号，避免跨页并列产生歧义。

## 前端结构

新增按需加载的 `HumanLeaderboardPage.vue`，不进入游戏首屏主包。`HumanApp` 将 `/leaderboard` 识别为独立 view；直接访问该地址时不激活对局写入者、不加载棋盘榜单和个人最佳。由对局页进入时先等待当前移动落盘并暂停界面输入，再切换路由，返回对局时复用现有恢复检查。

榜型、变体、周期、定式和页码由一个规范化路由状态管理；浏览器前进后退不重复入栈。每个筛选结果在本次页面会话内按 ETag 缓存。玩家名、数字列和分页按钮沿用当前 Play 主题；等级徽章复用分析海报的等级色，但改成适合表格的小尺寸，不复制 Canvas 绘制代码。

## 更新与回填顺序

1. 增加总榜字段、实力事实表、最佳表、版本状态和索引。
2. 扩展封局、Verse 导入、人工审核／撤销、回放补齐后的派生数据更新。
3. 在 `save_summary` 成功路径写实力事实；增加资格撤销和评级版本重建路径。
4. 从现有 `human_player_ratings`、`human_player_statistics` 和 `human_analysis_summaries` 回填。分析回填只解析小型 JSON，不读取回放。
5. 增加完整榜单 catalog／分页接口及权限、分页、并列、过期测试。
6. 增加独立页面，最后移除旧完整榜单浮窗状态与一次读取 100 项的代码。

重点测试包括：第 50／51 名分页、超长用户名、同分跨页、空榜、非法筛选；近 168 小时边界和过期后次佳递补；Verse 回填和归属撤销；隐藏局与人工批准；同一玩家多局／同局多定式不重复占位；评级版本重建不读取回放；公开 API 不泄露 `weighted_score`。
