# 公共分析库与“帮 TA 分析”设计

## 定位

对局站不再区分“私有任务历史”和“公共分析成果”。公开归档对局的分析统一进入一个分析库：任何登录用户都可以选择别人的公开对局、支付自己的 Token 并实际重新运行分析；分析结果属于原对局主人，允许展示时可被所有人查看。

后台仍须保存支付者和任务执行记录，用于扣费、限流、退款、审计和故障处理。这是内部运行信息，不构成另一套用户可见的私有成果页。

四种身份保持分离：

1. `initiator_user_id`：选择定式、支付 Token、占用个人并发和 artifact 配额；
2. `subject_user_id`：对局主人，拥有分析成绩、排行榜记录、展示图署名和头像；
3. `viewer_user_id`：查看允许展示的摘要与阶段回放；
4. 公共成果：以 `对局 + 定式 + 目标 + 分析器版本 + 指标版本` 唯一标识。

## 可分析的对局

别人只能为满足以下条件的对局创建分析：

- `status='sealed'`；
- `visible=1`；
- `eligibility='eligible'`；
- `archive IS NOT NULL`；
- `has_replay=1`；
- 对局所属账号当前允许正常公开访问。

以上条件应封装为一个统一后端判断，供任务创建、摘要读取、分析库搜索、原局跳转和 artifact 下载共同使用。

Verse 继承局与本站归档局地位相同。只有成绩而没有补全回放的记录不能分析，按钮置灰；补全并验证回放后即可分析。

主站“测试－分析”上传的普通文件不进入这个公共分析库。用户可以先下载公开对局再从主站上传分析，但该上传任务只是临时计算，不改变对局站公共库；从对局站入口创建的任务才按归档对局 ID 更新公共库。

## 用户入口

本人和其他玩家的历史记录都显示同一种分析入口：

- 本人对局：`分析`；
- 他人对局：`帮 TA 分析`；
- 没有可用回放：按钮置灰。

入口不因结果已存在、未过期或正在运行而消失。每次确认都执行新的任务、按完整报价扣费并返回本次结果。弹窗可以提示“分析库已有结果”或“相同分析正在运行”，但不能把它转换成免费读取或复用操作。

查看现有成果使用独立的`查看分析`入口，不与`帮 TA 分析`混在一起。

任务弹窗继续支持一次选择多个定式。对局 ID 和对局主人由后端从归档读取，前端不能提交或覆盖 `subject_user_id`。报价处明确写出：Token 从当前登录账号扣除，结果和署名归入对局主人。

报价接口同时返回当前的库容量边界。若该对局明显早于当前最早保留时间，应在确认前提示“本次会正常分析和收费，但结果可能不会收入分析库”。这只是预估；最终是否录入仍以任务完成时的实际文件大小和容量状态为准。

## 每次重跑与去重

分析库的唯一键为：

`source_run_id + pattern + target + analyzer_version + metric_version`

唯一键只用于归并展示与存储，不用于跳过计算。每次任务都产生自己的运行记录和暂存 artifact；成功后原子更新唯一成果项：

- 替换摘要为本次成功结果；
- 用本次阶段 `.rpl` 替换该项原有 artifact；
- 将 `last_analyzed_at` 更新为本次完成时间；
- 将 `expires_at` 重置为 `本次完成时间 + 保留期`，不在旧过期时间上累加；
- 更新 artifact 的配额归属为本次发起人，并释放被替换文件对上一发起人的占用；
- 记录本次任务创建时的主人展示设置。

分析库只长期保存阶段 `.rpl` 和小型摘要，不把 TXT、完整 ZIP 或输入副本登记为公共成果。分析任务自己的 TXT 与完整 ZIP 保留 1 小时，供发起人在完成页立即查看或下载；上传原文件在任务完成并完成素材转换后删除。

失败任务不得覆盖已有成功摘要、缩短其有效期或删除原 artifact。失败只影响本次支付结算和内部任务状态。

同一成果可以并行重跑，因为用户明确选择并支付了每一次计算。为避免完成顺序造成错误：

- artifact 和摘要以最后成功完成的任务为当前版本；
- `expires_at` 只能向后更新，不能被较早任务的迟到完成缩短；
- 展示快照按任务创建序号更新，不能由较早创建但较晚完成的任务倒写；
- 发布使用临时目录和事务，详情接口只能看到一整套旧产物或一整套新产物；
- 被替换 artifact 先标记 superseded，短暂宽限后删除，避免正在下载的请求中断。

每次都重跑会增加服务器成本，因此仍执行个人排队/运行并发、全站最多 60 个等待项、Token 余额和同账号提交频率限制。可以允许同一结果同时存在多个付费任务，但不允许一次双击或网络重试重复创建；创建接口必须接受客户端幂等键。

## 对局主人展示设置

账号设置新增：

`允许我的对局分析在分析库中公开展示`

建议默认开启，因为被分析的源对局本身已经公开；设置必须做账号级服务器同步。

每次创建分析任务时记录：

- `listing_snapshot`：任务创建时对局主人的设置。

成果的公开条件为：

`源对局当前公开 && 成果 listed=1`

`listed` 是单向状态：

- 成果首次写入时，以该任务的 `listing_snapshot` 决定是否展示；
- 已经公开的成果不会因主人后来关闭设置而隐藏；
- 关闭设置只影响此后尚未公开的成果；
- 一个未公开成果以后在设置开启时再次分析，可以转为公开；
- 公开成果不会再变回未公开，除非源对局本身被隐藏、撤销资格或删除。

因此成果更新使用：

`listed = existing.listed OR current_execution.listing_snapshot`

设置文案应明确写成“允许今后对我的对局所做的分析出现在分析库”，避免让用户误以为关闭后会撤回既有成果。默认值为开启。

任务运行期间设置发生变化时，以任务创建时的快照为准。并发任务无论以什么顺序完成，都只能把 `listed` 从 0 改为 1，不能倒写为 0。

不允许展示时，发起人仍能在本次任务完成界面查看本次返回结果，但结果不会进入任何用户可检索的持久前端列表，也不能通过 summary ID 或 artifact ID 绕过展示设置长期访问。后台保存必要的审计与扣费记录。

## 分析库的“完整”与“展示”

数据库在容量允许时保存成功成果项，包括 `listed=0` 的项；普通用户接口只返回满足公开条件的项。因此前端展示列表可以只是完整分析库的公开子集。

隐藏项只允许站长在管理页查询。普通用户不能通过顺序 ID、搜索、排行榜、个人主页、分享链接或 artifact 下载判断隐藏项是否存在。

展示设置同时控制：

- 公共分析库列表和详情；
- 玩家主页上的分析成果；
- 分析成绩排行榜；
- 阶段 `.rpl` 在线打开；
- 分析成绩单和分享链接。

它不改变原始对局本身的公开状态，也不影响对局的普通分数排行榜。若未来需要“允许详情但不参加分析榜”等更细设置，应新增独立选项，首版不混合多个含义。

## 独立分析库页面

建议路径为 `/analysis/`，顶部导航名称为`分析库`。

列表的一条数据表示一个唯一成果项，而不是一次付费任务。相同对局的多个定式可以在视觉上归组，但每个成果有自己的链接、摘要、阶段列表和过期时间。

筛选项：

- 玩家用户名；
- 变体；
- 定式一级、二级和目标；
- 来源：本站、Verse、其他导入；
- 对局结束时间；
- 分数范围；
- 阶段回放是否仍在有效期。

排序项：

- 对局结束时间；
- 分数；
- 同一变体、定式、目标和版本内的分析等级或拟合度。

分析库固定按原对局结束时间倒序，游标使用 `run_ended_at + entry_id`。页面可以显示“最近重新分析”，但该时间不参与顺序，重新付费分析也不能使旧对局上浮。

列表仅查询窄表，使用游标分页，不读取 archive、summary/report BLOB 或 `.rpl`。每项展示：

- 对局主人头像和用户名；
- 变体、分数、对局日期和来源；
- 定式与目标；
- 等级、平均拟合度、最大连续最优和阶段数；
- 最近分析时间和阶段回放过期时间；
- `查看分析`、`查看原局`、`帮 TA 分析`。

artifact 过期后仍保留摘要，阶段按钮置灰；任何登录用户都可以再次付费运行，成功后替换 artifact 并重置有效期。

## 分享图与身份

摘要详情接口必须返回服务器确认的：

- `subject.id`；
- `subject.display_name`；
- `subject.avatar_url`；
- `subject.profile_url`。

分享图、成绩单、详情页、个人主页和分析排行榜一律显示对局主人。不能使用当前登录用户，也不能信任路由传入的玩家对象。

发起人默认不公开署名。若以后增加“由某人赞助分析”，应由发起人主动选择，并且不改变成果归属。

## 阶段回放权限

满足有效公开条件的成果，其摘要和阶段 `.rpl` 可允许游客查看，以保证分享链接能够直接打开。文件仍不暴露服务器路径：

1. 详情接口返回不可猜测的 `artifact_id`；
2. 查看者申请只用于该 artifact 的短期签名凭据；
3. 回放页用凭据读取 `.rpl`；
4. 后端在签发和实际下载时都重新检查源对局资格，以及成果中已经固化且只增不减的 `listed` 状态；不读取主人当前的开关来撤回旧成果。

匿名用户按 IP 限频，登录用户按账号限频，并保留全局下载并发上限。建议初始值为匿名 10 次/分钟/IP、登录用户 20 次/分钟/账号、全站最多 4 个并发读取。

源对局被隐藏、撤销资格或删除后，即使旧签名尚未过期，下载接口也必须拒绝；签名不能成为源对局权限的快照。主人后来关闭“今后展示”设置不影响已经公开的成果。

## 数据模型

### `analysis_library_entries`

- 唯一成果键各字段；
- `subject_user_id/source_run_id`；
- 当前 `summary_id`；
- `listed/first_listed_at/last_analyzed_at/expires_at`；
- 最近一次执行的 `listing_snapshot`；
- `artifact_owner_user_id`；
- `artifact_count/active_bytes`；
- 当前版本及公开索引字段。

### `analysis_library_executions`

仅作为内部运行和审计信息：

- `job_id/work_index`；
- `initiator_user_id/subject_user_id/source_run_id`；
- 成果键；
- 报价、实际扣费、退款状态；
- 排队、开始、完成时间与最终状态；
- 幂等键；
- 创建时展示快照和请求序号。

它不提供普通用户列表接口，也不保存 TXT、ZIP 或长期输入文件。

现有 `human_analysis_results` 可继续作为分析排行榜和公共检索的窄事实表。`human_analysis_summaries` 的唯一键需要补充 `analyzer_version`；不能再用单一 `job_id` 表示成果所有者。

## Token、配额和清理

- 每次确认都完整报价并扣除发起人的 Token，不因库中已有结果而免费。
- 对局主人不扣费；成果和分析榜成绩归对局主人。
- artifact 占用计入最后一次成功更新它的发起人 50/100 个文件限额，以及全站 4 GiB 和至少 4 GiB 安全余量。
- 替换成功后释放旧 artifact 对上一发起人的配额；替换失败保持原归属和文件。
- 上传原文件在任务完成并完成素材转换后删除；任务 TXT 与完整 ZIP 保留 1 小时，随后清理。
- 内部任务审计长期保留；公共成果、摘要和阶段 `.rpl` 受分析库容量限制。

分析库以文件实际字节数执行全站 4 GiB 上限，并始终保留至少 4 GiB 磁盘安全余量。容量不足时完全按照原对局结束时间处理，不能参考分析时间：

1. 先淘汰 `run_ended_at` 最早的成果，时间相同时按稳定的 `entry_id` 顺序；
2. 新任务完成后，如果它的原对局时间早于当前容量边界且没有空间，则只向发起人返回本次结果，不录入分析库；
3. 对旧对局重新付费分析不能刷新其容量优先级，也不能把它挤到新对局之前；
4. 被容量淘汰的成果从公共分析库、玩家页分析成果和分析排行榜一并移除，artifact、公开摘要和公开索引删除；内部扣费与任务审计仍保留；
5. 清理以一个唯一成果项为原子单位，不留下只剩部分阶段的分析。

容量判断在本次文件全部生成并校验后、正式发布前完成。若候选成果无法录入，任务仍视为分析成功并正常收费，因为计算已经完成，完成界面应明确提示“结果已返回，但该对局较早，未收入分析库”。本次生成的 `.rpl` 作为任务临时产物保留 1 小时，供发起人立即查看或下载，随后删除；它不构成私有历史，也不占用公共分析库容量。

需要防止一种配额边界：若新发起人已达到 artifact 上限，不能先删除当前公共成果再尝试发布。应先在暂存区完成分析和校验，确定可腾出该发起人名下的旧 artifact 后再原子替换；无法满足配额时本次任务返回明确错误或只保存摘要，不破坏旧成果。

## 接口调整

- `GET /api/human/runs/{run_id}/analysis/options`：读取公开可分析对局，返回权威 subject 和已有成果提示；
- `POST /api/human/runs/{run_id}/analysis/quote`：始终为本次选择完整报价；
- `POST /api/human/runs/{run_id}/analysis/jobs`：以当前账号作为 initiator，每次创建真实任务，要求客户端幂等键；
- `GET /api/analysis/library`：只返回有效展示成果，窄表搜索和游标分页；
- `GET /api/analysis/library/{entry_id}`：在每次读取时复核展示条件；
- `POST /api/analysis/replays/{artifact_id}/open-link`：只为有效展示成果签发短期链接；
- `GET /api/analysis/replays/{artifact_id}`：下载时再次复核展示条件；
- 站长接口：查看完整成果、内部执行、展示快照、扣费和失败原因。

不再提供面向用户的“我的分析任务”持久列表。任务进行中的进度仍可由创建任务的会话和现有 job 状态接口查看；任务结束后，只有允许展示的成果进入公共前端历史。

## 仍需注意的问题

1. **展示设置只影响未来**：文案必须明确；已经公开的成果不会因后来关闭而撤回。
2. **重复运行造成置顶刷屏**：公共列表固定按原对局时间排序。
3. **并发覆盖**：摘要、artifact、有效期和展示快照需要分别定义更新顺序，不能简单地最后写入者覆盖所有字段。
4. **幂等与重复扣费**：允许主动重复分析，不等于允许双击、超时重试或反向代理重放造成重复任务。
5. **过期时间**：每次成功从完成时重置保留期，不累计叠加；失败不改变旧日期，容量顺序始终只看原对局时间。
6. **隐藏成果的信息泄露**：隐藏项不能出现在分析榜、个人页计数、搜索提示或可猜测详情接口中。
7. **服务器压力**：用户明确要求每次真实运行，因此不能用缓存省略计算；只能依靠 Token、个人/全局并发和频率限制控制负载。
8. **算法版本**：升级后必须形成新的唯一成果版本，旧结果不能被新版静默覆盖或混入同一分析榜。

## 实施顺序

1. 拆分 initiator、subject 和 viewer，建立统一可分析与可展示权限函数。
2. 增加默认开启的账号级展示设置，并在任务创建时保存快照。
3. 增加成果表与内部执行表，补齐 analyzer version、请求序号和客户端幂等键。
4. 改造任务完成流程：暂存、校验、原子替换、过期时间重置、旧 artifact 延迟删除和配额转移。
5. 在本人及其他玩家历史记录接入统一分析弹窗和`帮 TA 分析`入口。
6. 新增 `/analysis/` 列表、详情、筛选、游标分页、分享图和游客阶段回放。
7. 补齐重复运行、乱序完成、设置切换、旧局拒绝入库、容量淘汰、任务失败、配额不足和越权测试。
