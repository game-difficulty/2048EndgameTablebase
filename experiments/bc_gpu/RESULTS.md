# BC GPU 首轮实验结果

日期：2026-09-23。硬件：RTX 4080 SUPER / Ryzen 9 9950X。

后续 free10-512 大表实验见 [GPU 生成、compact 与 FamilyChain](FREE10_RESULTS.md)。本文仍记录首轮小定式基线。

**已完成真实 CUDA 回算、完整自生成层的位级正确性，以及可复现吞吐基线。**
驻留计算有明显潜力，搬运与工作集大小会显著压缩收益；以下结果不是 free12 全流程加速比。

## 正确性

| 自生成定式 | 出 4 概率 | 完整生成层中的累计局面数 | GPU 逐层回传与 CPU 对照 |
|---|---:|---:|---|
| free6 → 8 | 25% | 250 | 全部位级一致 |
| free8 → 32 | 25% | 79,230,434 | 全部位级一致 |
| free8 → 32 | 10% | 79,230,434 | 全部位级一致 |
| free8 → 32，零裁剪 future | 10% | 79,230,434 | 胜率、keep 集合及压紧行序全部一致 |
| free9 → 16 | 10% | 14,360,934 | 全部位级一致 |

free8 两种概率复用同一批自行生成的位置，分别执行 CPU 回算；不将它们计为两套不同局面。
free8 与 free9 两个非平凡定式合计 **93,591,368** 个生成局面。
从种子正向生成到完整终止边界，没有使用随机胜率或截断 horizon。

额外验证：

- 327,680 个棋盘、1,638,400 个移动／D4 输出，GPU 对照生产 CPU primitives 全部一致。
- 9 种概率各 483,470 组数值样本，共 4,351,230 组，包含整数边界、2 的幂边界、0／终值、1..16 空位；全部位级一致。
- 每一层的 GPU BC 解码与 CPU 导出的棋盘逐项一致。
- 全部 GPU 胜率 SHA256 与对应 CPU value 文件一致，`results/audit.json` 记录审核及源码指纹。

首版普通 FP64 归约在 10% 概率下发现 20,571,241 个差异，未通过验证。现在的基线使用 CPU80 兼容整数归约，不采用误差容忍掩盖这一问题。

## free8 → 32：代表层吞吐

使用 10% 概率和零裁剪后的未来层。下表的层编号是小砖和，包含 F 的真实 raw sum = 262144 + 小砖和。
所有数字为 9 次重复的中位数；GPU 配置为 128 threads/block。

| 小砖和 | 当前局面数 | CPU 16 线程 API | CPU 32 线程 API | GPU decode+solve Event | GPU 启动+同步 wall | GPU 重新加载已备索引，含传输 |
|---:|---:|---:|---:|---:|---:|---:|
| 38 | 1,820,480 | 24.016 ms | 21.786 ms | 0.529 ms | 0.548 ms | 13.970 ms |
| 48 | 4,479,360 | 49.067 ms | 43.498 ms | 1.065 ms | 1.083 ms | 22.110 ms |
| 52 | 5,225,513 | 43.736 ms | 35.381 ms | 1.056 ms | 1.076 ms | 22.445 ms |
| 62 | 4,344,163 | 27.905 ms | 25.435 ms | 0.746 ms | 0.765 ms | 20.100 ms |

以小砖和 52 为例：5,225,513 局面中 4,516,441 个非终局；不是仅测终局写常数。
CPU 16 线程约 119.5 Mrows/s，GPU 驻留的 decode+solve 加启动同步约 4,855 Mrows/s。
这两者是 **API 与驻留设备计算** 的对照，不能将约 40.6 倍直接解释为整条生成／回算流程的收益。

“重新加载”计时采用预构建实验设备索引、热 OS 文件缓存。CPU API 列则不包含 future 加载建索引。因此最后一列用于量化 GPU 搬运代价，并非完全对称的端到端 CPU/GPU 对照。
GPU 64/128/256 threads/block 三种配置均通过全值核对，这些层上的差异较小，暂用 128 作为基线。

原始证据：`results/free8_32_p010_benchmark_sparse.json`。未裁剪 future 的对应结果也保留在 `results/free8_32_p010_benchmark.json`。

## 第二定式交叉检查

free9 → 16，10% 概率，未裁剪 future；同样使用 9 次中位数。

| 小砖和 | 当前局面数 | CPU 16 线程 API | GPU decode+solve，启动同步 wall | GPU 重新加载已备索引，含传输 |
|---:|---:|---:|---:|---:|
| 32 | 161,652 | 3.727 ms | 0.139 ms | 8.494 ms |
| 38 | 1,048,302 | 9.460 ms | 0.319 ms | 16.616 ms |
| 42 | 1,724,922 | 10.849 ms | 0.361 ms | 16.968 ms |
| 46 | 1,879,115 | 8.305 ms | 0.285 ms | 14.500 ms |

这些较小层若每次重新加载，传输成本甚至超过 CPU 已驻留的回算时间；把 GPU kernel 跑快不足以保证整个步骤更快。

## 缓存容量压力：必须降低对大定式的预期

free8 小砖和 52 的两个压紧未来表，设备 hash/bitmap/rank/value 合计 49,835,356 bytes（47.5 MiB），小于此 GPU 的 64 MiB L2。
因此上面的高驻留吞吐有很好的缓存条件。

额外实验将这两个表复制为相互独立的设备数组，每个真实源棋盘选择一个 replica 执行同样回算，所有值仍与 CPU 完全相同。它保持源局面、移动及数值计算不变，扩大未来随机访问范围；这是合成缓存实验，不是更多真实局面。

| 复制数 | 未来表字节数 | 回算 kernel 中位数 | kernel 吞吐 |
|---:|---:|---:|---:|
| 16 | 797,365,696 | 5.187 ms | 1,007.5 Mrows/s |
| 32 | 1,594,731,392 | 7.489 ms | 697.7 Mrows/s |
| 64 | 3,189,462,784 | 10.276 ms | 508.5 Mrows/s |
| 128 | 6,378,925,568 | 12.251 ms | 426.5 Mrows/s |

最后一组实际分配了约 5.94 GiB 未来表；所有组逐值核对通过。
与能放进 L2 的小工作集相比，吞吐明显下降。复制版多了选择 replica 的开销、也改变了局部性，故不能拿它直接预测 free12 加速比；但它表明后续设计必须把工作集和缓存纳入判断。
原始证据：`results/capacity.json`。

## 本轮结论及范围

1. BC 压缩表示、移动和高频随机查表确实能在消费 GPU 上执行；在本轮完整图上能做到与当前生产 CPU UInt32 位级一致。
2. 默认 p4=0.1 的 CPU long-double 舍入是实质兼容性问题，本实验已解决受支持范围内的归约并独立验证。
3. 显存驻留／增量复用未来窗口比继续微调 block 大小更值得优先做。
4. 百 MiB 级真实数据和约 5.94 GiB 合成工作集均已测量，但没有证明 free12 的 12 GiB 适配或完整流程收益。
5. GPU 生成、GPU position compact、FamilyChain partial/scratch 流水线及 BCAD 都是后续工作，没有在当前报告中冒充完成。

复现入口与完整计时定义见 [README](README.md)。当前仓库的生产算法文件未被本实验修改。
